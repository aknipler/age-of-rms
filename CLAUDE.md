# CLAUDE.md — Age of RMS

Free, open-source Windows desktop app (Tauri 2 + React/TypeScript, thin Rust) that lowers the barrier to writing Age of Empires II: DE Random Map Scripts. Its centerpiece is the **Breakdown editor** — a block-based UI that is a *view over the RMS code*: every edit becomes a minimal text patch, and the code is always the single source of truth. Also ships a Monaco code editor with RMS highlighting/hover docs, an approximate map preview, and an Advanced Tools pane. DE only. GPL-3.0.

**Before starting:** read this file, `PLAN.md` and `CREATION_PLAN.md` (both one level up, in the parent `AOE2_projects/RMS` folder), and the design spec for whatever subsystem you're touching (Sec. Design docs).

Do not write Ash's name in comments, commit messages, PR's or docs. Speak in the imperative mood, or omit references unless it is absolutely necessary such as in LICENSE.

When writing README files or human facing docs, do not mention "Phase" at all, avoid exaggerative words like delve, unleash, game-changing, tapestry, pivotal, moreover, furthermore, navigate, or "it's worth noting". Avoid sentence structures like balanced triads ('the X, the Y, and the Z') or lazy contrasts ('It’s not just X, it’s Y'). Remove unnecessary filler adverbs and introductory transition phrases. Avoid em dashes, hyphen, colons and semi-colons as punctuation marks. Semi-colons can still be used before a list.

## Teaching mode — read this before you write any code

Ash is using this project to learn **TypeScript, React, and desktop app development**. He comes from Python/C++, so the language basics transfer; the JS/TS ecosystem and React's model do not. **This has not been happening enough — fix that.**

Treat it as a requirement, not a nicety: a session that ships correct code and teaches nothing has half-failed. Concretely:

- **Explain the non-obvious decision, never the syntax.** Don't explain what a loop or a function is. *Do* explain why this is a `useRef` and not `useState`, why an effect needs a cleanup function, why `unknown` is better than `any` here, why this type is a union rather than an enum.
- **Name the concept out loud** — "this is a *discriminated union*", "this is a *stale closure*", "this is *lifting state up*", "this is *structural typing*". Naming it is what makes it searchable later; an unnamed explanation teaches nothing durable.
- **Comment the "why" in the code you write.** The codebase is also the textbook. `src/hooks/useDocument.ts` and `src/breakdown/BreakdownPane.tsx` are the standard to match — they explain stale closures, StrictMode's double-invoke, and why the Monaco model is the source of truth.
- **Distinguish idiom from project choice.** Say whether something is standard React/TS practice or a decision specific to this codebase, so Ash learns transferable habits and doesn't cargo-cult our quirks.
- **Prefer showing the alternative.** "I used X here; the obvious alternative is Y, which breaks because…" is worth more than a description of X alone.
- **End a non-trivial session by offering 2–3 questions** that check understanding of what was built (CREATION_PLAN's "learning check" habit).

Keep it proportionate — a few sentences at the decision points, not an essay per file.

## Hard rules

- **Design specs are authoritative.** If a spec seems wrong or ambiguous, **stop and escalate** — do not improvise a deviation.
- **`src/parser/**` and `src/breakdown/patch/**` must not import React, Monaco, or Tauri.** They must run unchanged in a bare web worker and in plain-Node Vitest.
- **Never silently drop content.** Anything unparseable or unrepresentable degrades to an explicit raw node / read-only raw card. Never crash, never vanish.
- **Code is the only source of truth for Breakdown.** No parallel model; every user action becomes a `TextEdit` against the source, then a re-parse re-renders. Never re-print code.
- **The Sec.4.8 property gate must be green before any UI is wired to the patch engine.**
- **Vocabulary is data-driven.** Commands/attributes/directives/sections/labels come from `reference/data/language.json`. Hardcode no RMS vocabulary.
- **Reference data is a positive resolver, never a negative authority.** Finding a name in `game-constants.json` / `language.json` / `predefinedLabels` proves something; *not* finding one proves nothing — the constants DB holds 31 of several hundred, and DE-official maps branch on engine labels the archived guide never documented. Never report a diagnostic whose evidence is absence from our data. (Established by the `validate()` measurement, 2026-07-31; a naive reading of parser-design Sec.8 produced 11,623 corpus diagnostics, mostly this mistake.)
- **A reference-data hit says what a name *is*, never what the engine has already done with it.** The corollary, and the harder half. `predefinedLabels` records names the engine *may* define — every one of the 138 is a runtime condition, so `#define EMPIRE_WARS` is a working override in any game that isn't Empire Wars, not a shadowed no-op. Before a diagnostic asserts engine *behaviour*, name the observation behind the claim. (Same-day review of the above, RMS0302 split into RMS0302/RMS0312.)
- **A rule established in one pass is not established in the passes that predate it.** The positive-resolver rule above was written while building `validate()`, applied thoroughly there, and never carried back to the parser — where `RMS0200` still asserts "the engine will silently ignore it" on nothing but a name's absence from `language.json`, 858 times on the corpus (`docs/known-issues.md` BUG-005). When a session lands a rule, grep for the older code the rule now governs. Same shape as the rev-6 lesson that a prerequisite marked done in one representation is not done in the others. (2026-07-31 parser audit.)
- **A declared `default` must satisfy its own declared `min`/`max`.** Enforced by `npm run validate:reference`. Two `language.json` arguments shipped `min 1 / max 16 / default 0`, transcribed from a guide line that documents both the range and 0-means-flat; the parser then false-warned on all 461 corpus uses of `base_elevation 0`. When transcribing a range from the guide, read the sentence next to it.
- **A control that can only confirm is not worth printing.** RMSTEST_22 measured elevation's bias along `y`, and printed `mean x` purely as a sanity check on an axis nobody had questioned. `mean x` came back 0.336 against 0.500, which is how the whole 45° map rotation was found — the guide's "south" is a *screen* direction on the `y−x` diagonal, and every revision through rev 6 had modelled the wrong axis. Add the orthogonal reading you expect to be boring; when it is not, it is the result. (2026-08-01.)
- **Prefer an observable to an argument.** Every `[tune]` constant tested on 2026-08-01 was wrong in *kind* rather than magnitude — an axis, a shape, a reference length, a missing degree of freedom — and three of four had survived multiple rounds of critique unchanged. `border_fuzziness` is the sharpest case: rev 3 reasoned to a flat coin-flip, rev 4 reasoned harder to a per-tile Bernoulli, both moved toward the truth and stopped far short of it, and one map settled it in six runs. This is the same lesson rev 6's changelog recorded and it needed relearning at the constant level.
- **A per-run pass/fail gate can be stricter than the data requires.** All six RMSTEST_25 runs failed their own header's discard rule; the contamination was separable and 258 clean samples came out of six "failed" runs. Check whether the bad part can be filtered before throwing away the run.
- **A check that has only ever passed proves nothing. Mutation-test it against the defect it exists to catch.** Introduce the failure deliberately, confirm the message is readable and the exit code is non-zero, then restore. This project has already shipped a unit test that *asserted* the `verified` bug it was meant to catch (Phase 4.0), and the `MAP_SIZES` ordering comment sat unenforced through the exact reordering it warned about (Sec.15 item 6). A green run is evidence about the code only once you have seen the check go red. (2026-08-01, `validate:reference`'s MAP_SIZES join.)
- **A fallback chosen to avoid an undemonstrated failure mode is still a guess.** `set_zone_by_team`'s treatment of un-teamed players was pinned on 2026-08-01 to the "graceful" reading — keep `playerNumber − 10` — because the literal `TeamNumber − 9` was argued to put team 0 in zone −9, collide with player 1's default, and collapse FFA maps into one landmass. **The premise was false**: RMSTEST_37 measured an un-teamed player carrying their own internal team number, so the collision never existed and the literal reading was right all along. Safety arguments feel different from modelling arguments and are not: both are arguments, and *prefer an observable* governs both. Corollary that made this expensive — the run written to test it (RMSTEST_29) could not discriminate, and its replacement (RMSTEST_34) failed in the exact way its own header's prediction 4 had described in advance. **A test whose header names its own failure mode should be redesigned before it is run.** (2026-08-04, Sec.15 item 14.)
- **Normalise before reading a profile across unequal bins.** Sec.6.2's disfavoured-half gradient was first read from raw counts per diagonal band and showed nothing, which would have closed item 11(a) as an artefact. The bands hold 4675 tiles down to 300; dividing by tiles-available reversed the conclusion and the gradient is real. Any "no trend" over bins of different size is a claim about the bins until proven otherwise. (2026-08-04.)
- **A shipped map is not a specification. Official DE maps contain bugged lines, and the engine's silence is why they survive.** A construct's *presence* in shipped scripts is not evidence that it is legal — the engine passes malformed lines silently, the affected code simply never takes effect in game, and nobody ever finds out. This session alone measured `set_loose grouping` 457 times across three official Battle Royale maps, `set_scale_by_group` 96 times in `includes/water_blending.inc`, and 15 valueless `#const SIZE` lines in one community map. **Before any frequency count is allowed to license a data change, ask what a player or author could have observed if the form were wrong.** If the answer is nothing, the count is worth nothing, however large and however independent. `ai_info_map_type.showType` was marked `optional: true` on 52 independent three-argument uses and reverted the same day: guide:475 lists `showType` **not functional on DE**, so the two forms are indistinguishable in game and no shipped script could ever have revealed which is correct. Independence (52 files, 20+ map types) ruled out a copy-paste artefact and still did not rescue it — that check answers "is this one observation?", not "could this observation have gone the other way?". Same shape as `avoidance_distance`. (2026-08-05, BUG-003.)
- **The guide licenses omissibility with a sentence, never with a `default:` notation.** The five arguments correctly flagged `optional` on 2026-07-31 each carry explicit prose — "if you specify the argument but omit the distance" (guide:1693), "**No argument**, or a value of 0 imposes no further restrictions" (guide:2719). Arguments carrying only `(default: N)` are the trap in both directions: `terrain_state` declares defaults on all four arguments and omits none, and `showType`'s `default: 0` proved nothing at all. **Look for the sentence. If there isn't one, the answer is UNDETERMINED, and undetermined means leave the data alone and say so** — it does not mean fall back to counting shipped maps. (2026-08-05, BUG-003.)
- **A fixture written before the checker existed is an untested assertion.** `test-maps/sample.rms` is a Phase 1.4 syntax-highlighting demo that sat in `corpus.test.ts`'s `ZERO_ERROR_ALLOWLIST` for months while being invalid RMS: `create_elevation` and `create_terrain` missing their required arguments, and `terrain_type` used inside `create_terrain` where `base_terrain` belongs. No gate caught it, and none was wrong to miss it — the allowlist checks zero *errors* and these are warnings. When a pass lands that can read an artefact for the first time, run it over the artefacts that predate it. (2026-08-05.)
- **A count is not a conclusion. Check that the uses are independent, and that at least one could have been observed to matter.** `avoidance_distance` was excluded from `language.json` as an author typo, then re-admitted on 2026-08-01 because it appears **320 times across three shipped DE-official scripts** — a number that reproduces exactly and proves nothing. All 320 are one copy-pasted `CIRCLE_*` template (so it is *one* observation, and "two Forgotten Empires maps" is one FE circle-generator copied twice), and every single use passes a constant defined as `0` — a no-op whether or not the engine implements it, so **no shipped script could ever have distinguished a real attribute from a discarded token**. Both checks were available and neither was run, in an argument whose entire content was a frequency. Contrast `building_architecture`, wrongly grouped with it: 52 uses of `2` against 20 of `1` is an author drawing a distinction, which is what usage evidence looks like when it means something. (2026-08-01, BUG-004 closed as not-a-bug.)
- **NEVER run `git checkout --`, `git restore`, `git stash`, `git clean` or any other tree-restoring command in this repo.** There is no safe use of them here. This working tree carries ~90 modified files and weeks of uncommitted work as its *normal* state, and git cannot recover what was never committed. On 2026-08-02 a `git checkout -- reference/data/language.json`, run to undo a formatting change, destroyed every uncommitted edit to that file back to 2026-07-22: all 138 `predefinedLabels`, the six BUG-003 `optional` flags, the `base_elevation`/`create_elevation` range fix, the four `nonFunctional` attributes, and both engine-verified note rewrites. **Undo an edit with the edit tools, the same way it was made.** Recovery took a VSS snapshot plus a transcript-mined replay of four changes, and only worked because a snapshot happened to exist. Related: `git diff` in this repo compares against a *stale* HEAD, so a large `+` count is usually accumulated real work, not churn from your own last command — read the diff before believing it.
- **A shipped file is not a source file, and not everything inside one is the language.** `$SpawnAvoidance` / `$heightLow` / `$infinite` were filed as an unmodeled DE templating feature on the strength of appearing in a DE-official *and* a community map, with "so whatever it is, it is fully supported syntax" written into the entry. They are unexpanded variables from the preprocessor both authors build with, so those files are simply broken at those lines and the warning was a true positive — the bug report had the sign backwards. Before treating an unfamiliar construct as language, ask whether the file is a build artefact: a second version stamp in the header (`BSV: 9.1.1` beside the map's own `Version: 2.6`), naming that breaks house style (camelCase among SCREAMING_SNAKE), and a symbolic word standing in for a number are all fingerprints. Note also that "official *and* community" was never two independent observations — one file is modified by the guide's own author and both share a `#define` template vocabulary. (2026-08-02, BUG-002(b) closed.)
- **Absence of one name proves nothing; absence of exactly the set a rule predicts is a measurement.** The positive-resolver rule above says never report on absence from reference data, and it is right — but it is not a ban on *reasoning* about a data set's shape. `language.json` recorded the guide's `teamSize` enumeration as irregular and transcribed-as-written because `TEAM1_SIZE1` was missing. Enumerating which of the 45 candidate names are *reachable* under the guide's own "a team needs ≥2 members" rule returned exactly the 29 present, with zero discrepancies either direction — so the enumeration was never irregular and the rule was already stated in prose two pages away. The distinction that makes this legitimate: a predicted set matching an observed set is evidence, one name's absence is not. Same shape as the `mean x` lesson below — add the reading you expect to be boring. (2026-08-01, Sec.15 item 4.)
- **A stage that silently produces a plausible output is harder to find than one that throws, and its damage surfaces as correct diagnostics somewhere else.** `lands.ts` shipped with no `grid.terrain` write at all: `stampOrigin` and `claimTile` set land ownership and nothing ever painted a land's `terrain_type`. Every map therefore rendered as one flat `base_terrain`, and the symptom that reached the bug report was **19,608 placement failures on one map** — every one of them a *true* statement about the grid it was given (`create_terrain { base_terrain DIRT2 }` really did have no DIRT2). All 1,170 tests passed throughout, because every stage's `place()` helper hardcoded `createTileGrid(dim, GRASS)` and asserted against a grid it had built itself. **When a stage's tests construct their own input, they cannot catch the previous stage failing to produce it — make the helper run the real pipeline.** (2026-08-07, preview review round 1.)
- **Time the thing before optimising it, and check the timeout is calibrated against a measurement rather than a budget.** "Preview generation is really slow" was reported, and the generator was indeed carrying two quadratic scans worth 545 million comparisons on one map. But the *reported* symptom was mostly a 1000 ms watchdog derived from Sec.11's 40 ms-per-stage budget: about a third of the corpus legitimately exceeds it, and the watchdog killed the worker, re-posted, re-armed, and repeated forever, so those maps never rendered at all. **A watchdog set below the real cost is a denial of service on your own feature**, and an unbounded retry makes a deterministic slowdown into an infinite loop. Measure the distribution first (median 458 ms, worst 3.8 s) and set the ceiling from it. (2026-08-07.)
- **Reference data being a positive resolver cuts the other way too: a resolver that only accepts one spelling of a name is a false negative factory.** Five stages each kept a private `terrainIdByName(constants, name: string)`. Only 78 of DE's 131 terrains have a callable constant, so scripts reach the rest by bare id (`terrain_type 26`) or by defining their own (`#const WOODIES 48`) — and both forms reported "this map's reference data doesn't know that terrain", which is exactly the diagnostic-on-absence the positive-resolver rule forbids. One shared `resolveTerrainId` now takes the written value, whatever form it is in. Resolution order matters and is testable: **game constants first, script `#const` second**, because the engine loads `random_map.def` before the script and `#const` is first-definition-wins. (2026-08-07.)
- **An "unrestricted" default is a claim, and against sparse reference data it is the strongest claim available.** `objectHabitat` returned `"any"` for any object outside `game-constants.json` — 16 entries of several hundred — so in practice every tree, animal and decoration a real script placed was exempt from terrain restrictions, and `AD4 - Pag - v1.2.rms` grew 21 of its 40 OLIVE_TREEs in open water. `"any"` reads like the cautious choice next to guessing, which is exactly why it survived: it is phrased as declining to guess, but a preview has to put the object *somewhere*, so it silently guesses "anywhere". **When a fallback still produces output, ask which wrong answer it produces, not whether it is abstaining.** Related, and the reason the fix was safe: check whether the two candidate defaults are symmetric before agonising over them — land objects dominate, water objects almost always carry an explicit `terrain_to_place_on`, so one default is wrong rarely and recoverably and the other was wrong constantly. (2026-08-07, preview review round 2.)
- **A cap justified by "no real script hits this" must name the measurement, or it is a silent truncation waiting to happen.** S4's clump cap was `4 * dim` "chosen generously enough that no non-pathological corpus script hits it". Nothing had been counted: at `dim` 200 it stopped every command at 800 clumps, and `number_of_clumps 9320` — the guide's OWN worked example — appears 23 times in one section of one corpus map. The standard convert-all-of-this-terrain idiom was converting a twelfth of it, and because the failure surfaced as a slightly-wrong-looking map rather than an error it survived all of Phase 4.3. **Prefer a bound that is a fact about the work to a budget that is a guess**: the replacement is `min(clumpCount, eligiblePool.length)`, exact because a clump claims at least one tile, and it bounds the 999999999-clump pathological case better than the [tune] constant did. (2026-08-07.)
- **"Not simulated" in a spec scopes the RENDERING of a thing, not its semantics — check which one you are reading.** Sec.9 lists terrain_mask's visual blending as not simulated, and an implementation cited that to collapse `terrain_mask 1` and `2` into one behaviour, reasoning that "the over/under distinction would be invisible in the renderer's own contract even if modelled exactly". The distinction is not visual at all: mask 2 changes WHICH TERRAIN OWNS THE TILE (guide:1502-1509, "provides new properties"), and therefore what every later `base_terrain` match, habitat check and automatic-object rule sees. Every mask-2 command was a no-op for the rest of the pipeline. When an exclusion is invoked to justify skipping work, state which observable it covers. (2026-08-07.)
- **A sentinel that collides with a real value is not a sentinel, and a zero-filled typed array is the easiest place to hide one.** `grid.layer` used `0` for "no layer"; `0` is GRASS's terrain id. Every consumer — the renderer's tint, `base_layer` matching, `layer_to_place_on` — was unable to tell "nothing layered here" from "layered with GRASS", and it was wrong in both directions on real maps. It reads as initialisation rather than as a decision, which is why it survived: `new Uint16Array(n)` looks like allocating memory, not like choosing a value. **When a typed array's default doubles as a meaningful value, say so out loud or pick a value outside the domain** — `UNREACHABLE` in the same file had already got this right. (2026-08-07, preview review round 3.)
- **A "not simulated" note can hide the thing the author actually cared about. Check what the construct is FOR before deciding it is cosmetic.** `second_object` was dropped with a `secondObjectNotDrawn` note, which reads like a rendering nicety — an extra object stacked on a main one. guide:2211 recommends it as the standard way to "bypass terrain restrictions by using an invisible placeholder object as the main object", so on real maps the MAIN object is a placeholder nobody wants to see and the second object is the fish. Dropping it made `AD4 - Pag - v1.2.rms` generate zero fish and `Menindee_AUS_v2.3.rms` lose every pond fish, reported as a placement failure rather than as a missing glyph. Same shape as the `terrain_mask` finding one round earlier: an exclusion was written about the visible half and applied to the semantic half. (2026-08-07, preview review round 4.)
- **Two rules that are each correct can compose into a result that is obviously wrong, and the bug report will name the composition.** Pag's bordered islands always hugged their border edges and never reached the map corner. Neither `borderBounds` nor RMSTEST_25's measured cross-shaped origin region is implemented wrongly; intersecting `x, y ∈ [0, 80]` with "reject when |x−100| > 34.2 AND |y−100| > 34.2" leaves an L-shaped sliver, and that is the whole of the effect. **The right response was to work out the intersection and write down the run that decides the open half** (is the engine's cross absolute, or relative to what the borders leave? RMSTEST_25 only ever measured unbordered lands), not to soften a measured rule because its consequence looked odd. (2026-08-07.)
- **A fix that removes the symptom is not the same as a fix that states the rule. Construct the observation that separates the candidate models.** `create_elevation` was summing across commands, so one map hit the elevation ceiling everywhere. The first fix — measure each command from `base_elevation` instead of from the running total — removed the symptom completely and was still wrong: `MaxHeight` is an ABSOLUTE CEILING, so two lands at `base_elevation` 5 and 2 under one `create_elevation 6` both top out at 6, not 11 and 8. The distinguishing case (two lands at DIFFERENT base elevations under ONE command) was never constructed, because the map that prompted the work did not contain one. **When a change is reached by asking "what would stop the bad output", check what else fits that constraint.** (2026-08-07, preview review round 4b.)
- **When mutation-testing by text substitution, assert the match is unique — the mutation is safe, the RESTORE is where the damage happens.** Reverting a mutant in `lands.ts` replaced the first occurrence of a four-line pattern that appears in two functions, silently relocating a bound from `sampleReservoir` into `neutralOrigin`. Ten tests went red with no obvious link to the edit. A mutation test is only cheap if putting the code back is exact. (2026-08-07.)
- **An argument that rules out a model must name the set it quantifies over, and check that set is the one in dispute.** The automatic beach step shipped conditional on `beach_terrain` because an unconditional step "converts the waterline straight back, and every beach tile borders water by construction, so the undo is total". Locally valid, and it quantifies over beach the STEP laid — a waterline, one tile wide — while the idiom it was protecting is about beach a land is MADE of, where only the outermost column reverts and the interior keeps the conversion. Both halves of the fork were argued with corpus counts of exactly the maps that would have separated them, and neither count was ever pointed at a specific tile. **When a claim of the form "every X is Y" decides a design, write down which X you have in hand and construct the X you do not.** (2026-08-08, Sec.15 item 28.)
- **A guide line that reads like documentation OF an attribute is a rule ABOUT the block, and an attribute with no test is where they hide.** Three now, all in `objects.ts`, all found by someone running the map rather than by review: `max_distance_to_other_zones` is a MINIMUM ("Minimum (NOT maximum)", in the guide's own capitals), `terrain_to_place_on` does not lift the terrain table, and `ignore_terrain_restrictions` carries `Requires: set_place_for_every_player or place_on_specific_land_id` — unmet, the whole `create_object` places **nothing**, silently, 47 times across the corpus. Every one of the three had zero coverage in either direction when it was wrong, and each read as consistent with its neighbours at a glance. **When transcribing an attribute from the guide, read the header lines (`Requires:`, `Mutually exclusive with:`, `Game versions:`) as behaviour to implement, not as prose about the entry** — and write the test for whichever attribute you would least expect to need one. (2026-08-10, RMS0315.)
- **The exception to a rule belongs inside the thing that computes the rule, not at the call site that knows about the exception.** `ignore_terrain_restrictions` lifts the terrain table for every habitat except `shore`, which keeps its beach anchor and merely gains the shallows. Written as `if (flag) skipHabitatCheck()` that survives exactly until the next caller; written as a mask that answers "which tiles qualify, given the flag" it cannot decay, and the two call sites got shorter. Same shape as `beachTerrain` moving out of `create_terrain`'s own clump and into the single beach pass. (2026-08-10.)
- **Every interactive UI element wraps in `<HelpTip id="...">`** with a matching entry in `reference/data/ui-help.json`, as it's built — including "temporary" UI.
- **New dependency ⇒ say `npm install` in the same breath**, and add its `@types/*` package if it needs one. (Bitten twice: `ajv`, `@types/node`.)
- TypeScript strict mode; functional components with hooks only; Prettier defaults (don't hand-format).

## Environment: sandbox caveats

Agent sessions have repeatedly hit these; they are workflow rules, not project bugs.

- **The repo's `node_modules` can't run Vitest inside the Linux sandbox** — it was installed on Windows, so Rollup fails with `Cannot find module '@rollup/rollup-linux-x64-gnu'`. **Do not install Linux binaries into the mounted `node_modules`** (it persists back to Ash's machine). Instead mirror `src/` + `reference/data` + `test-maps` into a `/tmp` scratch project with a fresh `npm install -D vitest typescript @types/node` and run there.
- **The sandbox mount has served stale or truncated file contents** on several occasions. The file-editing tool's view is authoritative. Line-count-check any mirror against source before trusting a test result.
- `tsc --noEmit`, `eslint`, and `validate:reference` all run fine against the real mount (no Rollup dependency).
- **`npm run dev` (plain Vite, no Tauri host) cannot render this app past its first frame.** `HelpSettingsContext`/`GenerationSettingsContext`/`useDocument.ts` all call the Tauri store plugin synchronously on mount; outside the real Tauri host process `window.__TAURI_INTERNALS__` doesn't exist, so the call throws (`Cannot read properties of undefined (reading 'invoke')`) and crashes the whole tree before anything below `AppContent` renders — confirmed 2026-08-06 while trying to visually verify the preview pane's worker swap. A browser tab pointed at a `tauri dev` session's own Vite port doesn't help either: the IPC bridge is injected into the native WebView2 window specifically, not the port it happens to share, so a plain Chromium tab still can't see it.
- Ash's local run is the real confirmation. End a session by listing the exact commands for him to run.
