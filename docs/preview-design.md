Six revisions have been folded in; **only the current round's changelog lives here (Appendix A). The rev-2 through rev-6 changelogs moved to `docs/build-log.md`** — under a do-not-deviate banner, historical self-litigation competes with the spec for an implementer's attention, and rev 4 proved the risk concretely by leaving a withdrawn decision standing in Sec.3.10 while its correction lived in an appendix. Read the body as normative; if the body and any appendix disagree, the body wins and the appendix is stale.

**When two places in the body disagree, the dated one wins, and the undated one is the bug.** Rev 7 was largely a hunt for exactly that: four sections still carried a rule the same document had withdrawn elsewhere, and the body-beats-appendix tiebreak above gives no answer to a body-against-body conflict. **Rev 6 was different in kind from its predecessors, and this still governs how to read the doc.** Revisions 2 through 5 were critique rounds: one reader arguing with the text against the guide. ## 1. Goals and non-goals

Goals, in priority order:

1. **Honest approximation.** The preview conveys *layout* — where lands, terrains, hills, and objects plausibly end up — never a claim of pixel- or seed-accuracy. Every rendering is labeled approximate (Sec.9). We would rather show nothing than show something confidently wrong.
2. **Structured failure instrumentation.** Every placement function returns a structured failure reason on a miss — never bare `false`. This is a hard design requirement from CREATION_PLAN 5.2: the Generation Consistency Checker consumes this instrumentation, and retrofitting it is painful. See Sec.7 — it is the contract, not an afterthought.
3. **Never throws.** Like the parser: any ParseResult (including ones full of RawNodes and diagnostics) produces a PreviewResult. Unsimulatable regions become SimulationNotes (Sec.9), not exceptions.
4. **Fast enough for live update.** Full pipeline on a 200×200 map inside a web worker, debounced on code change, **superseded requests discarded by id** rather than cancelled. Budget in Sec.11. Cheap enough that 5.2 can run ~1000 generations in seconds. (Through rev 6 this goal said "with cancellation" while Sec.10 withdrew per-run cancellation and gave the reasons; Sec.10 wins and the goal is corrected to match. 5.2's batch loop is separately cancellable **between runs**, which is what CREATION_PLAN 5.2's UX asks for and is a different mechanism — see Sec.11.)
5. **Deterministic.** Same (ParseResult, settings, seed) → identical PreviewResult, byte for byte, **across JS engines and engine versions**. This is what makes the re-roll button meaningful and the 5.2 Monte Carlo reproducible. ECMAScript does not bit-specify `Math.sin`/`cos`/`pow`/`sqrt`, so **the generator uses none of them** (Sec.8) — the player ring reads a precomputed fixed-point sine table, clumping weights are integer buckets, distance comparisons are done on squared values. Byte-for-byte is a claim we can only make if the arithmetic is exact, so the arithmetic is exact. **This goal is worth exactly as much as its lint rule, which Sec.8 now specifies concretely and Sec.13 gates** — through rev 6 it rested on the phrase "lint-enforced if practical" against an `eslint.config.js` that contained no such rule.

Non-goals: seed parity with DE (our seeds mean nothing in-game and the UI must never imply otherwise); full-fidelity rendering (later milestone, possibly via game-state reading per PLAN.md); simulating everything in Sec.9's exclusion list; incremental regeneration (full regen is cheap; the API is pure so incremental can come later).

## 2. Position in the architecture

```
ParseResult ─┐
refDb (language.json + game-constants.json) ─┤
PreviewSettings (playerCount, mapSize, teams) ─┼→ [worker] generatePreview() → PreviewResult
seed + PreviewOptions ─┘                              │
                                                      ├→ 4.2 canvas renderer (grids, objects, markers)
                                                      ├→ status-bar notes / Problems-adjacent surfaces
                                                      └→ 5.2 Consistency Checker (reports, batch mode)
```

The generator is a **pure function hosted in a web worker** (same discipline as the parser: no imports from React, Monaco, or Tauri anywhere under `src/preview/generator/` — it must run in a bare worker and in Node/Vitest unchanged). This is now a lint rule rather than a convention; Sec.8 gives its exact configuration and Sec.13 gates it.

**One import boundary is deliberately open, and it is worth stating because the lint rule would otherwise look like it forbids it.** `src/preview/generator/` **may** import `src/generationSettings/generationSettingsConstants.ts` (for `MapSize`, `TeamNumber`) and `src/generationSettings/teamModel.ts` (for the Sec.3.1 canonicalisation). Both are plain modules with no React or Tauri import, so they satisfy the purity rule, and importing `teamModel.ts` is the whole point of its having been written pure — the alternative is a second copy of the canonicalisation rule, which is the drift Sec.10 forbids for `Span`. Nothing else under `src/generationSettings/` is importable; `GenerationSettingsContext.tsx` next door is a React module and the lint rule must catch it.

The renderer (4.2) is a separate, dumb consumer: it draws whatever grids and marker lists it is given and owns zoom/pan/diamond projection; it contains no generation logic. Renderer contract, minimally: terrain fill from `previewColor` (Sec.12), `layer` as an overlay tint, **elevation as brightness shading** (lighten toward the light-source edge per height step, darken opposite — cheap slope shading, no 3D), cliff glyphs, object dots/glyphs colored by `category`, numbered player markers, and the Sec.9 badge.

Consumers and their needs:

- **Preview pane (4.2/4.3):** the **S6** snapshot + objects + players + notes; re-roll and Current/Final toggle. **Note what this consumer does *not* read: neither Current nor Final reads S1–S5.** Both draw a final grid (Sec.5 — Current is a separate run over a truncated script, not a stored stage).
- **Stage scrubber (4.2, not yet built):** S1–S5. **This is the only consumer of the intermediate snapshots and it is the reason `collectSnapshots` exists.** Stated because the 2026-08-01 Current/Final decision removed the last *shipped* reader of S1–S5, leaving six snapshots, an 8 MB budget, a typed-array copy per stage boundary and the API's only cost knob with nothing pointing at them — which an implementer would reasonably read as an oversight and delete. It is not an oversight: `StageSnapshot[]` is cheap to keep, 4.2 builds its hardcoded fixture against this exact type list (Sec.10, Sec.14), and re-adding a per-stage copy after the fact is more expensive than carrying it. If 4.2 ships without a scrubber, revisit — do not delete on sight.
- **Consistency Checker (5.2):** `reports` with `collectSnapshots: false` for cheap batch runs across a player-count matrix.
- **Status bar (existing):** resource totals stay AST-derived (Phase 2.5) — the preview does NOT replace them in v1; a note in 5.2's design may reconcile the two later.

## 3. Script instantiation — evaluating what the parser deliberately didn't

The parser never evaluates conditionals, randoms, or math (parser-design Sec.1 non-goals; Sec.2.2 explicitly assigns those semantics to us). Stage 0 of every generation is an **instantiation pass** that walks the AST and produces a flat, per-section list of concrete commands — mirroring the engine's token-filter model.

Rules (each cites its source):

1. **Environment.** Predefined labels derived from `PreviewSettings` (Sec.10 — `{ playerCount, mapSize, teams }`; `mapSize` is the *label* input and is independent of `dim`, see Sec.4). The label universe comes from **`language.json`'s `predefinedLabels`** (Sec.12 item 1) — **now populated**, 138 entries, each with a `category` the generator switches on and, for `mapSize` entries, `dimensions` plus the matching `MAP_SIZES` value. The generator reads the same array `validate()` reads; two hand-rolled lists that drift is exactly the failure mode CLAUDE.md's "vocabulary is data-driven" rule exists to prevent. Keep the `refDb.predefinedLabels ?? []` guard and its one prominent SimulationNote ("label data is missing; every conditional is being evaluated as undefined") as a regression backstop — never a hardcoded label list.
   Which labels are set: the map-size labels for the active size — both legacy and modern per Sec.4's table, and **note the names are offset**: the app's Normal (200×200) defines `LARGE_MAP` *and* `MAPSIZE_NORMAL`; `MAPSIZE_LARGE` is the next size up (220×220, legacy `HUGE_MAP`); Giant has no legacy label at all. Use Sec.4's table columns verbatim — guessing the pairing by name produces silently wrong branch selection on every size-aware map. `<N>_PLAYER_GAME` for the active player count, `DE_AVAILABLE` and its version-detection chain set, standard-lobby defaults for the rest (no REGICIDE, no EMPIRE_WARS, etc.).
   **Teams — the control now exists (2026-08-01), and this replaces the solo-team premise.** Sec.15 item 4 is closed: the generation-settings pane carries a per-player team assignment, so the preview no longer guesses. `PreviewSettings.teams` (Sec.10) is the generator's read-only view of it.

   **The input.** One **selected** team number per player, `0 | 1 | 2 | 3 | 4`, where **0 means un-teamed** — that is `assign_to`'s own vocabulary, not a UI invention (guide:1001, "0 is for un-teamed players"), and it is why the picker shows `-`. Teams cap at 4 because the engine's label vocabulary does (`0_TEAM_GAME`…`4_TEAM_GAME`, `PLAYERx_TEAM0`…`PLAYERx_TEAM4`). The array is **always length 8**, indexed `player − 1`, and entries at index `≥ playerCount` describe players who are **not in the game**: ignore them everywhere, including in team sizes. Stated explicitly because the settings pane deliberately *retains* assignments for players you have temporarily counted out, so a generator that reads all 8 will silently invent teammates.

   **The selected number is not the label number, and this is the trap.** The guide says so three separate times (guide:1000, 3121, 3151): team numbers in `TEAMn_SIZEm`, `PLAYERx_TEAMy` and `assign_to AT_TEAM` "refer to lobby order, not the number chosen by the team". S0 therefore derives a **canonical** numbering before defining any label:

   1. Group players `1..playerCount` by selected number, ignoring 0.
   2. **Drop every group with fewer than 2 members** (guide:1004, "Teams containing only 1 player do not count as teams"; guide:3115 says the same for team count). Those players become un-teamed. A player sitting alone on team 1 is a perfectly legal lobby and the settings pane accepts it without complaint — the engine simply does not read it as a team.
   3. Order the surviving groups by their **lowest player number** (that is what "lobby order" means here) and number them 1, 2, 3, 4. **This step is `[verify]` — see the open question below. It is the one part of the team model that has never been checked against anything, and `src/generationSettings/teamModel.ts` already implements it.**
   4. Every player not in a surviving group is canonical team **0**.

   So a lobby of `-, 3, 3, -, 1, 1, 2, -` canonicalises to `0, 1, 1, 0, 2, 2, 0, 0`: selected team 3 becomes canonical team 1 because player 2 appears first, and the lone selected-team-2 player drops to un-teamed. **Do not skip this step and use the picker's numbers directly** — it is invisible in a 2v2 (where the numbers usually coincide) and wrong in every lobby where somebody picked team 4 first.

   **The ≥2 rule provably governs team *sizes* too, and the guide's own list is the proof.** The `teamSize` enumeration in `predefinedLabels` looks irregular — `TEAM0_SIZE1` exists, `TEAM1_SIZE1` does not — and the data's own `notes` field said so, transcribing it as written rather than completing it by inference. It is not irregular. Enumerate which of the 45 candidate `TEAMn_SIZEm` names are *reachable* under the rules above (real teams need ≥2 members, team 0 is the un-teamed remainder, ≤8 players) and you get **exactly** the 29 the guide lists, with nothing present-but-unreachable and nothing reachable-but-absent. `TEAM2_SIZE7` is missing because team 1 would need 2 more for 9 players; `TEAM4_SIZE3` because 2+2+2+3 is 9. Note the shape of this argument, because CLAUDE.md's hard rule forbids the lazy version: the claim rests on the *match between a predicted set and the observed set*, not on any single name's absence. Absence of one name would prove nothing; absence of exactly the sixteen a rule predicts, and no others, is a measurement.

   **⚠ The same check on the category next door FAILS, and it lands on step 3. `[verify]` — Sec.15 item 17, 2026-08-05.** The argument above was never run against `playerInTeam`, and it does not survive there. Of the 40 `playerInTeam` names in `predefinedLabels`, **only 34 are reachable under step 3**, because numbering teams by lowest player number makes player *k*'s canonical team at most *k*. These six are unreachable in every one of the 488,275 lobbies at 2–8 players, and all six are present in the data and marked `verified: true`:

   `PLAYER1_TEAM2`, `PLAYER1_TEAM3`, `PLAYER1_TEAM4`, `PLAYER2_TEAM3`, `PLAYER2_TEAM4`, `PLAYER3_TEAM4`

   **Three things make this worth a verify slot rather than a shrug.** First, the guide **enumerates both lists name by name**, in the same style, in adjacent paragraphs of the same section (guide:3121–3150 for `teamSize`, guide:3151–3191 for `playerInTeam`) — so this is not a formula transcribed into a full grid, and the two lists are not different kinds of source. Second, the pruning of the `teamSize` list is *meticulous*: dropping `TEAM2_SIZE7` requires noticing that team 1 needs two members and 2+7 exceeds 8. An author that careful, writing the next list down the page, would have pruned six names from the grid if step 3 were the rule. Third, there is a numbering rule under which **all 40 are reachable** — order the surviving groups by ascending *selected* number rather than by lowest player number. Under that rule a lobby where player 1 picked team 4 and players 3–8 filled teams 1, 2 and 3 puts player 1 on canonical team 4, and `PLAYER1_TEAM4` is a real label.

   **The two candidate readings, and what each costs:**

   1. **Step 3 is right** (lowest player number) and the guide simply wrote the `playerInTeam` grid out in full. Then `teamModel.ts` is correct, six data entries are present-but-unreachable, and Sec.3.1's set-match argument stops being *independent* evidence for the ≥2 rule — it becomes a fact about how the guide's author pruned one list. The ≥2 rule itself still stands on its own prose (guide:1004, guide:3115).
   2. **Step 3 is wrong** and the numbering is by ascending selected team number. Then all 40 names are reachable, the guide is consistent across both lists, and **`teamModel.ts` and every label this section derives are wrong for any lobby in which the lowest-numbered player did not pick the lowest-numbered team** — which is common.

   Note what does *not* discriminate: `teamSize` reachability is identical under both readings, since it depends only on the partition sizes and not on which team gets which index. So the 29-name match is evidence for the ≥2 rule under either, and evidence for step 3 under neither. Note also that guide:976 glosses "lobby order" for *players* as slot order ("the first person in the lobby is player 1"), which reads toward reading 1 by analogy and is the strongest thing pointing that way — an analogy, not a statement about teams.

   **This is settleable in one run on the existing instrument** and must not be settled by argument: put players 1–2 on selected team 3 and players 3–4 on selected team 1, branch on `PLAYER1_TEAM1` versus `PLAYER1_TEAM2`, and generate. Until it is, treat step 3 as the working rule (it is what is built) and do not repeat the reachability argument as support for it.

   **Related, and it belongs with this item:** `Michi.rms`, a DE-official map, branches on `TEAM1_SIZE1` (line 167), `TEAM2_SIZE1` (580) and `TEAM2_SIZE7` (889) — three names the reachability argument says cannot exist (`de-official-map-issues.md:290`). That is consistent with the argument (the branches are simply dead, which is what that document concluded), and it is also exactly what a wrong reachability argument would look like from the outside. Sec.12 item 9's "a script using a missing name is a script bug rather than a data gap" is asserting that three blocks of a shipped official map never run; it is probably right and it should be checked by the same run.

   **Labels set** (resolve every name through `predefinedLabels` — construct-and-trust is what the data-driven rule exists to prevent):
   - `<k>_TEAM_GAME` where `k` is the number of surviving teams. Exactly one is defined, and **`0_TEAM_GAME` is defined for an all-un-teamed lobby** — the old solo-team fallback defined no team-count label at all, so FFA scripts branching on `0_TEAM_GAME` took the wrong branch.
   - `TEAM<n>_SIZE<m>` for `n = 0..4`, `m` = that canonical team's member count, `0` for teams that do not exist. Team 0's size is the un-teamed count.
   - `PLAYER<x>_TEAM<y>` for `x = 1..playerCount`, `y` = that player's canonical team. Players above `playerCount` get no label.

   **What this retires.** `grouped_by_team` is now modelled rather than degraded (Sec.6.1); `set_zone_by_team` groups teammates (Sec.6.1); team connections produce real pairs (Sec.6.5); Sec.9 item 12's **banner note is withdrawn**. The banner existed because a Team Islands script rendered under solo teams is a plausible-looking lie, and that failure mode is gone. One drawer-level note survives in its place, keyed `"teams"`: when a script uses a team construct and the declared lobby has **no** teams, say so plainly — the preview is then correct, but the author is probably looking at the wrong lobby.

   **One thing the control does not fix.** The assignment is a **declared** lobby, not a prediction of any real one. A published map meets whatever the lobby hands it, so team-arranged scripts still want the 5.2 consistency sweep across configurations rather than one preview.
2. **`if`/`elseif`/`else`:** select the first branch whose condition label is defined in the environment (user `#define`s included, in stream order). Deterministic, not random.
3. **`start_random`/`percent_chance`:** roll once per RandomNode from the stage-0 RNG substream (Sec.8). Model: roll `r` = uniform integer 1–100; branches claim cumulative ranges in declaration order, truncated at 99 (guide:3007); a branch fires when its range covers `r`. **The 100th percent is never chosen** (guide:3010) — `r`=100 is always the no-branch outcome, so even totals summing to exactly 99 or 100 leave a 1% no-branch chance; totals <99 leave a larger one.
   The truncation rule is uncontroversial — guide:3007: "if the total exceeds 99%, only the first 99% will have a chance of occurring". The two statements that pin the *boundary* sit apart: guide:3006 says "if the total percentages add up to *less than* 99%, there is a chance that none of them get chosen", and guide:3010 — tacked onto the `percent_chance 0` bug bullet — says "the 100th percent is never chosen". They are not in conflict; the first states a sufficient condition for a no-branch outcome, not an exclusive one, so a 99 total leaving 1% unclaimed is consistent with both. The model above simply follows the second, which is the only statement that pins the boundary. Rev 4 framed this as resolving a contradiction and spent a verify slot on it; both were overstatements.
4. **Symbols:** `#define` marks defined; `#const` first-definition-wins, including silent no-op when shadowing a predefined name (parser-design Sec.8). `#undefine` does nothing.
5. **`rnd(a,b)`:** evaluated at consumption time from the current substream, uniform integer inclusive.
6. **Math expressions (ArgNode `expr`):** implement parser-design Sec.2.2 *exactly*: strict left-to-right, **no precedence, no nested parentheses** (a nested `(` operand is silently not-a-number — the engine drops it; do NOT implement standard precedence out of habit), constants resolve to numeric values, `inf`/`-inf` native, floats flow through, divide-by-zero → 0, `%` is **truncation toward zero** and `x % 0` → left operand truncated toward zero, rounding to integer (0.5 up) only where a float meets an integer-only slot. **Negative-float modulo: implement truncation toward zero for all operand signs**, matching the rest of this bullet, and leave a code comment pointing at `docs/parser-design.md:438` item 18. That item is **still open** — it is phrased there as a question with no answer in the build log — so this is a stated default, not a transcription of a result. Through rev 6 this bullet read "implement whatever the in-game test showed", which under a do-not-deviate banner instructs an implementer to go and read a test that does not exist; it is also in the wrong document for anyone to find. Tracked as Sec.15 item 19.
7. **`behavior_version`** (0–2): a stream variable; the value in effect when a land command is instantiated governs that land's tile accounting (Sec.6.1). We treat 2 as 1 (guide reports no observed difference) with a SimulationNote.
8. **`override_map_size`** (36–480, clamps): applied if it is in effect **before the first land command**; later overrides are recorded as a SimulationNote and ignored (the engine technically re-sizes mid-script; not worth simulating — flagged in Sec.9's list). Scaling attributes use the overridden area.
9. **RawNodes and unknown commands:** skipped, one SimulationNote each with the node's span ("this region isn't simulated in the preview"). Includes (`#include_drs`/`#includeXS`): one prominent note — "this map depends on include files the preview cannot see; the preview is missing whatever they generate."
10. **Duplicate attributes within a block:** last-wins (guide:167 states this directly — "if you duplicate an attribute or use mutually exclusive attributes, the final one will apply"), EXCEPT attributes flagged `repeatable` in language.json, which accumulate (parser-design Sec.8 — the same rule that keeps Breakdown from corrupting connection blocks). **Read the flag from the data. Do not hardcode the name list** (CLAUDE.md hard rule: vocabulary is data-driven). The flags **have now landed** — `spacing_to_specific_terrain`, `replace_terrain`, `terrain_cost`, `terrain_size` (that last is the "connection radius attribute"; rev 3 named the category rather than the attribute) — so rev 3's mandated hardcoded fallback list is withdrawn.
    Five attributes carry the flag today, `avoid_actor_area` included (it is cumulative in-engine — "The same object can avoid multiple actor areas", guide:2857, and its own example stacks six). Read the flag; do not maintain a copy of that list anywhere in `src/preview/`.
11. **Duplicate sections merge; sections process in canonical engine order** — `PLAYER_SETUP → LAND → ELEVATION → CLIFF → TERRAIN → CONNECTION → OBJECTS` (guide:135, which lists all seven and notes "the sections can be written in any order, but the game uses them in the order above") — regardless of file order, matching the engine's merge behavior (parser-design Sec.4). **`<PLAYER_SETUP>` is not a pipeline stage** and has no snapshot: its contents (`direct_placement`, `behavior_version`, `override_map_size`, `random_placement`, `grouped_by_team`, `nomad_resources`, effect commands) are stream state that S0 folds into the environment and hands to S1 (Sec.6.1 consumes all three of the first named). Rev 3 omitted it from both the order and the pipeline while Sec.6.1 read from it.
12. **Namespaces collected up-front.** Two constructs register names that later commands resolve against, and both must be gathered during S0 before any stage runs, regardless of script position: `create_object_group` (registers a group name in the same constant namespace `create_object` resolves through — a `create_object` naming a group defined later in the file still resolves) and `create_actor_area` (guide:1991: "created before any create_object commands are handled, regardless of their position in the script"). Rev 3 pinned the actor-area rule inside Sec.6.6 but never said which stage does the collecting, and never mentioned object groups at all.

Output: `InstantiatedScript` — per-section arrays of resolved command records (numeric args final, attribute maps folded, each retaining the source span of its originating CommandNode for click-through and failure reporting).

## 4. The tile model

The grid is square, `dim × dim` tiles. **`dim` is derived inside the generator**, never passed in: `PreviewSettings.mapSize` (a `MapSize`, the app's label-bearing lobby size) determines the starting `dim` via the table below, and S0 may then overwrite it from `override_map_size` (Sec.3.8). Labels come from `mapSize` and do not change when `dim` does — `override_map_size 200` on a Tiny lobby is a 200×200 grid on which `TINY_MAP` is defined. Passing a bare `dim` into the generator, as rev 3's API did, throws away the only input Sec.3.1 can build the label environment from.

| App MapSize | Legacy label | Modern label | Dimensions | Area ratio (display only — never compute with this, see Scaling below) |
|---|---|---|---|---|
| Tiny | `TINY_MAP` | `MAPSIZE_TINY` | 120×120 | 1.4 |
| Small | `SMALL_MAP` | `MAPSIZE_SMALL` | 144×144 | 2.1 |
| Medium | `MEDIUM_MAP` | `MAPSIZE_MEDIUM` | 168×168 | 2.8 |
| Normal | `LARGE_MAP` | `MAPSIZE_NORMAL` | 200×200 | 4.0 |
| Large | `HUGE_MAP` | `MAPSIZE_LARGE` | 220×220 | 4.8 |
| Huge | `GIGANTIC_MAP` | `MAPSIZE_HUGE` | 240×240 | 5.8 |
| Giant | *(none)* | `MAPSIZE_GIANT` | 252×252 | 6.4 |

Legacy and modern names are **offset by one size** for Normal/Large/Huge — this is the guide's table (guide:3437), confirmed by its own live example (`elseif LARGE_MAP create_actor_area 100 100 …` — the center of a 200×200 map). Sec.3.1's environment sets both columns for the active row. The seven rows above are the sizes the app's `MapSize` picker offers; the guide's table also carries `MAPSIZE_MINI` (80×80) and the MORE_MAP_SIZES tier (`MASSIVE` 276 … `LUDICROUS` 480), which `predefinedLabels` must still contain even though no `MapSize` value selects them — a script may branch on them, and an undefined label is the correct, non-matching answer. `LUDIKRIS_MAP`/`MAPSIZE_LUDICROUS` = 480×480. `override_map_size` changes `dim` and defines **no** labels (Sec.4 opening paragraph).

**The runtime source for this table is `predefinedLabels`, not this table.** Every `mapSize` entry in `language.json` carries `dimensions` plus the matching `MAP_SIZES` value, so the generator resolves `PreviewSettings.mapSize` → `dim` by lookup (`category === "mapSize" && entry.mapSize === name` → `dimensions`) rather than from anything transcribed here. **That key matches two entries for every size except Giant** — the legacy and modern names both carry `mapSize: "Tiny"`, both carry `dimensions: 120`, and Giant has no legacy row — so take **either**; `npm run validate:reference` asserts the pair agrees. A plain `find` is correct and a `filter(...).length === 1` assertion would be wrong. Said explicitly because the duplication looks like a data bug at the call site and is not one: the two names differ by *which label the environment defines* (Sec.3.1), not by dimension. The table above is documentation of that data, and where the two disagree the data wins. This matters because the legacy/modern offset is exactly the kind of thing a fourth hand-typed copy gets wrong — and `tools-api-design.md` currently instructs creating one (`MAP_SIZE_TILES`, "sourced from the guide's Map Sizes table"), a cross-doc conflict adjudicated in `docs/tools-api-design-rev4-review.md` B1 in this doc's favour but not yet applied there.

(The `MAP_SIZES` ordering warning that stood here is **resolved** — Sec.15 item 6, 2026-08-01. The array now runs Huge (240) before Giant (252), and `npm run validate:reference` asserts it stays ascending by dimension, so the constraint is enforced rather than merely documented.)

**Scaling (pinned, and it differs from rev 3's fixture):** every `set_scale_by_size` / `set_scale_by_groups` / `set_scaling_to_map_size` / `set_scaling_to_player_number` computation uses **`declared × (dim² / 10000)`, computed exactly from the live `dim`** — *not* the "Area ratio" column above, which is the guide's rounded display value.

**The guide instructs the banned method in one place, so read past it deliberately rather than discovering it mid-implementation.** guide:3429 supplies both halves of this. It establishes the reference the formula uses ("Scaling uses map area, not side length… use a 100x100 = 10000 tile reference"), and then it tells the reader to "multiply your chosen number by the area ratio listed for a given map size to determine how many tiles/clumps/objects will be generated". That instruction is author-facing arithmetic, not engine behaviour, and it is provably a rounding *of* the formula rather than an alternative to it: every listed ratio is that size's area divided by 10000 and rounded to one decimal place (20736 → 2.0736 → 2.1; 48400 → 4.84 → 4.8; 63504 → 6.3504 → 6.4). A rounded column cannot be the thing the engine multiplies by, because it is derived from the thing the engine multiplies by. The tie-breaker is guide:3432: `override_map_size` means "any scaling will use the new map **area**" — the engine derives the factor from the live area, which no fixed table of one-decimal ratios can express.

**CONFIRMED in-game, exactly (2026-07-31).** `create_object GOLD { number_of_objects 400 set_scaling_to_map_size }` on Small, frameless and unconstrained so nothing could starve the count, placed **829** objects — `400 × 20736/10000 = 829.44`. The rounded-ratio model predicts 840. Measured with `tools/scenario-probe`, not by eye. So Sec.13's fixture asserting 829 stands, and guide:3429 is an author-facing simplification.

Two notes on how this was established, because the first instrument failed. Tile-count measurements of `create_elevation` came back at ~2.13× declared (853, 851 at declared 400; 428 at 200) — *above* both models — because **an elevation clump overshoots its tile budget by roughly 3%** during growth. A grown region measures what it reached, not what it was told to reach; an object count is counted, so it reads the budget directly.

**Both halves of that are now measured, not inferred** (RMSTEST_13, 2026-07-31). Running `create_elevation` with a literal `number_of_tiles 829` and **no** `set_scale_by_size` — deleting the scaling path entirely — still produced 863, 855, 851, 848 across four runs (mean 854.25, **+3.05%**). So the overshoot is in growth, and it survives the removal of scaling. **And because that unscaled mean matches the scaled runs' 853/851, `set_scale_by_size` demonstrably follows the same rule as `set_scaling_to_map_size`** — had elevation scaled differently it would have targeted a different budget and landed elsewhere. This doc previously asserted that equivalence; it is now evidenced.

A perimeter-driven skirt was also ruled out: at `number_of_tiles 25` the same map gives 26, 26, 27, 26. A 25-tile blob has a perimeter near 18 against ~102 for an 829-tile one, so a skirt would have added ~18 tiles; it added one. The overshoot ratio (20×) tracks the area ratio (33×), not the perimeter ratio (5.8×). Treat the +1 at budget 25 as a quantisation floor rather than a rate — one tile is the least any overshoot can produce.

**The rounding rule is also settled: truncation.** `number_of_objects 500` on Small (exact 1036.8) placed **1036** on three separate runs, never 1037. See the scaling paragraph above.

**One caution carried forward from how this was measured.** Object counts came back perfectly reproducible — 1036, three times — while elevation tile counts varied (853, 851 at the same declared value). Same scaling path, different variance, which places elevation's variance in its *growth*, not in the scaling arithmetic. It does not by itself prove the ~3% mean offset is growth rather than a different scaling rule for elevation; Sec.15 item 7d covers that. Consequence, stated because rev 3 shipped the contradiction: the guide's own worked example (guide:1259, "400 tiles × 2.1 = 840 on a small map") is *its rounded column applied by hand*; the exact computation gives 400 × 2.0736 = **829.44**. Sec.13's fixture asserts 829 (with the rounding rule below), not 840. **The engine TRUNCATES the fractional result — measured, not assumed (2026-07-31).** `number_of_objects 500 set_scaling_to_map_size` on Small is exactly `500 × 20736/10000 = 1036.8`, and three separate runs each placed **1036**, never 1037. So: `Math.floor` on the scaled value, and floor at 1 for any attribute whose declared value was ≥1. Revisions 3 through 6 of this doc all said "round half up"; that was never verified and is now known wrong. Note the two rules compose — `829.44 → 829` and `1036.8 → 1036` are both plain truncation, and the earlier 829 measurement could not distinguish them because its fraction was below .5.

**Coordinates:** tile `(x, y)`, `x, y ∈ [0, dim)`. `land_position %X %Y` maps to `(round(X/100·dim), round(Y/100·dim))` — **confirmed in-game** (Test 9, 2026-07-30): two lands both at `land_position 50 50`, one `base_size 7` and one `base_size 5`, came out exactly concentric on a 120-wide map, which pins `50 50` → tile (60,60). Corner semantics per the guide: (0,0) = west corner, (99,99) = east, (99,0) = north, (0,99) = south. Borders: `left_border` = southwest edge (x=0), `right_border` = northeast (x=max), `top_border` = northwest (y=0), `bottom_border` = southeast (y=max).

**Border percent → tiles is asymmetric, and the guide gives the worked example** (guide:885–886): "due to rounding, the exact number of tiles that a given % value corresponds to may not be the same for each side… to stop 2 tiles from the edge on a tiny (120×120) map, a value of 2 must be used for the top and left borders, but a value of 3 is needed for the bottom and right borders." **MEASURED (RMSTEST_16, 2026-07-31) — and the rounding is symmetric after all; the asymmetry is an off-by-one in the coordinate arithmetic.** The rule, matching all four edges exactly on two reproducible runs:

```
min_x = round(left_pct   /100 · dim)        max_x = dim − round(right_pct /100 · dim)
min_y = round(top_pct    /100 · dim)        max_y = dim − round(bottom_pct/100 · dim)
```

Declared 3/2/6/9 on a 120 map gives 3.6/2.4/7.2/10.8, so round-half-up predicts min_x 4, max_x 118, min_y 7, max_y 109 — and those are the measured values, to the tile, twice. **Every edge uses round-half-up.** Revisions 2 through 6 said floor on the low edges and ceil on the high ones; that is wrong. What the guide's worked example is really describing is the `dim` versus index-0 asymmetry above: the low edge's first tile *is* the rounded value, while the high edge's last tile is `dim` minus it, which costs one tile and is why a larger number is needed on the bottom and right to leave the same gap.

**Do not unify this with Sec.4's scaling rule.** Scaling *truncates* (measured: 1036.8 → 1036); borders *round half up* (measured: 3.6 → 4, 10.8 → 11). Two different rounding behaviours in the same engine, both measured, and a single shared helper would silently break one of them.

**Confirmed against the guide's own worked example (RMSTEST_17).** All four borders set to 2 on Tiny — the exact case guide:885 describes — produced `x 2..118, y 2..118` on both runs, which is what the formula predicts (`round(2.4) = 2`; `120 − 2 = 118`). It also *explains* the guide's sentence rather than merely coexisting with it: a declared 2 leaves tiles 0 and 1 empty on the low edges (a 2-tile gap) but only tile 119 empty on the high edges (a 1-tile gap), which is why "a value of 3 is needed for the bottom and right borders" to achieve the same gap. Read that phrasing as *the smallest integer achieving at least this*, not as an exact equality — a declared 3 actually buys a 3-tile gap, since `round(3.6) = 4`. Rev 4 gave one conversion rule for `land_position` and none for borders, so an implementer would have applied `land_position`'s symmetric `round` and been off by a tile on two edges of every bordered map. Two related facts also unstated: **negative border values are legal** (guide:887) as long as the land origin stays on the map, so do not clamp them at 0; and `circle_radius` is documented as 1–50 and float-accepting, as are borders in DE — carry both as floats through the percent conversion and round only at the tile boundary. The renderer owns the diamond projection of this grid; the generator never thinks in screen space.

**Layers** (typed arrays, allocated once per generation):

```ts
interface TileGrid {
  dim: number;
  terrain: Uint16Array;    // terrain id (index into refDb terrain table)
  layer: Uint16Array;      // base_layer / terrain_mask visual layer; NO_LAYER (0xffff) = none, NOT 0 — 0 is GRASS's terrain id, and using it as the sentinel made a real GRASS layer indistinguishable from an absent one in every consumer
  elevation: Uint8Array;   // 0-16
  cliff: Uint8Array;       // 1 = cliff tile
  landId: Int16Array;      // which land claimed this tile; -1 = base terrain
  zone: Int16Array;        // zone of the claiming land (defaults per Sec.6.1)
  occupied: Uint8Array;    // object occupancy (objects stage)
}
```

Derived masks (computed on demand, cached per stage): distance-to-terrain maps for spacing checks (one BFS distance transform per queried terrain id), forest-zone mask (tiles whose terrain is flagged `isForest` in refDb, plus placed tree objects, plus 1-tile adjacency — guide `place_on_forest_zone` semantics), water mask (`isWater` flag).

## 5. Pipeline stages, snapshots, and the Current/Final toggle

Stages run in fixed order; each ends with an optional snapshot (copy of the mutable grids at that point):

```
S0 instantiate → S1 lands → S2 elevation → S3 cliffs → S4 terrains → S5 connections → S6 objects
```

`PreviewResult.snapshots` holds one entry per stage S1–S6 when `collectSnapshots: true` (objects aren't in the grid; the S6 snapshot is the final grid plus the full `objects` list). Snapshots copy **only the renderable layers** — `terrain`+`layer`+`elevation`+`cliff`, 6 bytes/tile (`landId`/`zone`/`occupied` are generation state the renderer never reads): 6 B × 480² × 6 snapshots ≈ 8 MB worst case at Ludicrous — acceptable, and snapshots are skipped entirely in 5.2 batch mode.

**Current/Final toggle (per PLAN.md and the Breakdown side-panel mockup):**

- **Final** = the S6 result: full map, objects included.
- **Current** = **the script truncated at the user's caret. DECIDED 2026-08-01 (as a cursor LINE; sharpened to the caret's exact offset 2026-08-10 — see the block below consequence 2), and it is neither of the two readings this section previously weighed.** Both candidates assumed Current selects a *stage snapshot*; it does not. Current means "generate as if everything after this line were commented out", which is a **prefix of the script**, not a point in the pipeline. Rev 3's S1-vs-S2 question and the "stage being edited" extension are both moot and are withdrawn.

  Two consequences the snapshot model does not have, and 4.2 must not paper over:

  1. **It needs its own generation run, not a stored snapshot.** Truncating the source changes what every later stage does, so Current is `generatePreview(truncateAst(parse, pinnedLine), refDb, settings, opts)` — note the argument is the **truncated AST**, not truncated text, per consequence 2 below. (Through rev 6 this line wrote it as `parse of source[0..line]`, which is text truncation, one line above the paragraph forbidding text truncation.) Snapshots answer "what did the map look like after elevation"; this answers "what does this half-written script produce", which is the question an author actually has. Cheap enough — Sec.11 budgets a full run at ≤40 ms — but it is a second run per cursor move, so it debounces with the existing ~300 ms timer and is skipped entirely when the toggle is on Final.
  2. **Truncation must happen on the AST, not the text.** Cutting mid-block leaves an unterminated `create_land {`, so the tree is cut and the braces the author wrote are kept. Cutting the raw text would hand the parser a syntax error on every second cursor position and make the preview flicker between valid and broken.

  **THE CUT IS A CHARACTER OFFSET AND THE RECURSION GOES ALL THE WAY DOWN. DECIDED 2026-08-10, ON USE, AND IT REPLACES THIS SECTION'S LINE-GRANULAR RULE.** Consequence 2 used to continue: "the prefix is taken to the last complete top-level item at or before the cursor line, and a cursor inside a block includes that whole block." That is withdrawn. It made the cut round *up* to the end of whatever construct the caret was in, and on a real script the caret is nearly always inside a block — so a caret three attributes into a `create_land` drew the finished land, including the attributes below it that had not been written yet. The interesting constructs are exactly the ones it refused to cut, and watching one take shape is what Current is for.

  What replaces it, in one rule: **an item is kept when it BEGINS before the caret**, and an item the caret is inside is cut down rather than kept or dropped whole. So a block keeps the attributes above the caret and loses the ones below; an `if`/`start_random` keeps the branches above the caret and cuts the one the caret is in; a leaf (an attribute, a directive) is all-or-nothing, because half an attribute is not a thing the AST can hold. An item that starts exactly AT the caret is dropped, which makes the caret behave like the insertion point it is. What survives from the old rule is the part that mattered: the tree is cut, never the text, so what reaches the generator is always a well-formed script.

  **UI: a pin.** The cut point can be set explicitly rather than following the caret — put the caret where you want the map to stop, click the pin button, and the preview holds there while you keep editing and moving around. Unpinned, Current follows the caret. The pin is what makes this usable while scrolling, and it is the control the toggle needs beyond a plain two-state switch. HelpTip id `preview.pinLine`, added to the list below. **The pin follows the code** (decided 2026-08-10, same pass): it is an offset shifted through every edit by the same machinery that keeps the shared selection anchor on its card (`useShiftedAnchor`), so inserting lines above a pin moves the pin with them. A line number could not do that, and the first implementation that used one drifted the moment anything was typed above it.

  **The ignored remainder is shaded.** Current silently drops the rest of the script, and a map missing half its lands looks identical to a map whose lands failed — so from the cut point to the end of the document the code is dimmed (a Monaco inline decoration in the Code tab, a card class in Breakdown, both only in Current). This is not decoration: it is the only thing that distinguishes "not generated yet" from "generated and went wrong", which is Goal 1's own line.

**Both toggle positions draw a final grid, and neither reads S1–S5.** Final is the S6 grid of a run over the whole script; Current is the S6 grid of a run over the truncated script. Every run executes all stages regardless — reports and totals need S6 — so the toggle selects **which of two runs is on screen**, never which stage. (Rev 6 closed with "the toggle only selects which snapshot the renderer draws", which is the stage-snapshot model the DECIDED block above withdraws. It is deleted. The snapshots themselves are kept for the 4.2 stage scrubber, which is a different feature and the only thing that reads them — Sec.2.)

**HelpTip ids (mandatory per CLAUDE.md, enumerated here so 3.5's help-coverage audit has a checklist).** One already exists — `breakdown.sidePanel.previewToggle` (`ui-help.json:268`) — and its copy currently ends "Preview logic arrives in Phase 4"; **4.2 must rewrite that line** as part of shipping the toggle. ## 6. Stage designs

Every "pick a tile / grow a region / place a thing" operation goes through the instrumented placement layer (Sec.7) and draws randomness only from its stage substream (Sec.8). Heuristic parameters marked **[tune]** are 4.3 calibration knobs — start with the given value, iterate against real screenshots.

### 6.1 Lands (S1)

Engine model (guide <LAND_GENERATION> intro): land *origins* (square bases) are placed sequentially in script order; then **all lands grow simultaneously** from their origins until they hit their size target, a border, or another land.

**Base fill:** `base_terrain` (default GRASS) fills the grid; `base_layer` fills `layer`.

**Player lands** (`create_player_lands`, expanded to one land per active player):

- Default placement: origins on a circle. Radius: `circle_radius` values are a **percentage of map width** (guide:843), and so is our default — nothing here is in tiles. Two regimes for borders (guide:854 distinguishes them): the *default* circle's center = map center shifted by borders (borders shift the whole circle); an *explicit* `circle_radius` **ignores borders when placing origins** — center stays at map center — though growth remains border-constrained.
  - **No `circle_radius` at all:** radius **40**, radial variance **10**, plus **angular jitter of roughly ±7°**. **MEASURED (RMSTEST_24, 2026-08-01), 48 origins over six runs on a 120 map.** Three separate results:
    - **The percentage is of the FULL map width, not the half width.** Mean origin distance from centre was **50.44 tiles = 42.0% of dim**, against 48.0 for the full-width reading and 24.0 for the half-width one. The guide's bare "percentage of map width" (guide:843) admitted both and the two describe completely different maps; it is the full width. 40 stands as the default and is slightly low.
    - **Variance 20 is about twice too large.** Measured sd was 7.11 tiles, which for a uniform draw implies a half-range near 12.3 tiles, about 10% of width. Guide:849's "20 seems to be close" is the guide author's own hedge and it overshoots. Note the measurement conflates origin jitter with centroid displacement from asymmetric growth, but a 60-tile land can only contribute a tile or two of that, so the radial spread is dominated by real variance.
    - **The ring also jitters in angle, which no revision modelled.** Gaps between the eight origins came out 53.9, 40.2, 49.9, 39.2, 43.4, 44.2, 51.0 degrees — mean 45 as expected, spread ±7. Apply it per player after the whole-ring rotation offset.
  - **`circle_radius R V` given:** radius `R`, variance **`V`, default 0** when the argument is omitted (guide:847: "Variance - number (default: 0)"). Rev 3 let the 20 leak into this branch, which would have scattered a deliberately perfect ring. Three corpus maps write a bare `circle_radius 38` / `circle_radius 19` with no variance and mean a perfect circle.
  - **`circle_radius 0` disables circular positioning entirely** (guide:844: "0 will disable circle_radius") — fall back to the no-`circle_radius` default ring, *not* to radius 0. Treating 0 as an explicit radius stacks every player on the map center, which is both a visible lie and a guaranteed `originFallbackCenter` storm. **CONFIRMED in-game** (Tests 2 and 5, 2026-07-30): eight player islands on a water base, `circle_radius 0` versus the attribute deleted entirely, produced the same wide scatter with an empty centre across three seeds each. So 0 behaves *exactly as if the attribute were absent* — which also means it inherits the no-attribute variance, not the variance-0 default of the second argument. **That figure is ~10, not guide:849's ~20**: Tests 2/5 predate RMSTEST_24 and this line quoted the guide's estimate until 2026-08-02, contradicting the measurement three bullets above. Use the measured no-`circle_radius` branch wholesale — radius 40, radial variance 10, angular jitter ±7° — since "as if absent" means exactly that. ~~Note `language.json` declares `radiusPercent` with `min: 1`, so this legal idiom currently draws a false `RMS0203`.~~ **FIXED 2026-08-04** — `radiusPercent` now declares `min: -50`, guarded by `src/parser/__tests__/circleRadius.test.ts` and mutation-tested against the old bound.
  - **`circle_radius` NEGATIVE is a THIRD behaviour, and it is neither of the two above. MEASURED (RMSTEST_27, 2026-08-04)** — `circle_radius -20`, five runs on Tiny at 8 players, 34 origins. Mean radius **33.2 tiles = 27.6% of dim, CV 0.44**, against the default-ring branch's 50.4 tiles / CV 0.14 and against 24 tiles / CV 0 for an absolute-value reading. So it is **not** the disable sentinel, and it is **not** `|R|`. The distribution is scattered rather than annular (CV 0.44 sits nearer uniform's ~0.52 than a ring's 0.14) while still centre-biased relative to uniform (33.2 against ~45.9), and origins merged at 27% against RMSTEST_24's zero. The convenient answer — fold negative into the same branch as 0 so the data fix is one bound — was recorded as the prediction precisely because it was convenient, and it is refuted. **Model it as a scattered draw, not a ring, and mark the parameters [tune].**

    **The shape, since "scattered draw" is not implementable and rev 6 stopped there.** The two moments to hit are **mean radius `0.276·dim`, CV 0.44**, centre biased, origins permitted to merge. Neither obvious draw matches, and it is worth writing down why so 4.3 does not spend the afternoon rediscovering it: a **uniform radius** on `[0, 0.552·dim]` hits the mean but gives CV `2/√12 = 0.577` (too scattered), while a **uniform point in a disc** of radius `0.414·dim` hits the mean but gives CV `1/(2√2·⅔)` ≈ 0.354 (too annular — the `r·dr` weight pushes mass outward). 0.44 sits between them, so the distribution needs one shape parameter and cannot be either. **Start with a mixture of the two, weight `[tune]` fitted to CV 0.44**, which is monotone in the weight and therefore trivially solvable, and re-fit if a second run lands. `language.json`'s own note on this attribute says "Not yet modelled precisely" and is honest; the gap was here, not in the data. A second run at `circle_radius -60` would say whether the magnitude enters at all, which is the cheapest next question if anything ever depends on it.
  - With multiple `create_player_lands` commands, only the **final** radius applies (guide:856).
  - Angles: players evenly spaced, whole ring rotated by a random offset, each player's radius jittered by variance independently. Angles come from a precomputed fixed-point sine table indexed by `floor(3600·k/N)`, never `Math.sin`/`Math.cos` (goal 5, Sec.8).
- `grouped_by_team`: **modelled, and MEASURED (RMSTEST_36, 2026-08-04) — the ring is divided by GROUP count, not player count.** Distribute the **groups** evenly around the ring, where a group is a canonical team and **every un-teamed player is a group of one**, then lay each group's members along the ring centred on its slot. Ring radius and the whole-ring rotation are unchanged; the per-player ±7° angular jitter is **not** applied inside a group, since it would fight the spacing the attribute exists to set.
  **Evidence, and it is unambiguous.** Five runs at 4v4 gave two tight clusters of exactly four lands 176–180° apart (360/2). Three runs at **5v1v1v1** — the discriminating configuration — gave one packed arc of five spanning 24–32°, plus three lone players, arranged as **four groups at 89–91° (360/4)**, every origin at radius 79.6–80.7 on an 80-tile ring. The competing reading (space all eight players evenly at 45° and merely reorder so teammates are adjacent) predicts eight separate lands at uniform spacing and is refuted outright. The 5v1v1v1 runs also confirm the solo-player rule directly: players 6, 7 and 8 each took a full ring slot of their own.
  **The intra-team spacing is NOT 2·`base_size`, and this is unresolved.** guide:356 says "distance between team members is double the `base_size`", which at `base_size 3` is 6 tiles. Measured centre-to-centre spacing between consecutive teammates was **10–12 tiles at 4v4** and 8–11 tiles across the 5-arc (24–32° at radius 80), i.e. roughly **3.5–4·`base_size`**. Treat 2·`base_size` as a lower bound and the measured ~3.5× as the working figure **[tune]**. Caveat, and it is why this is not pinned: these are centroids of *grown* lands, not origins, and growth displaces a centroid. A run at several `base_size` values would separate the constant from the growth artefact. Note the shape of the discrepancy — a factor of about two on a reference length — is the same error the ring's own radius carried until RMSTEST_25.
  Mutually exclusive with `random_placement` (guide:345) and disabled by `direct_placement` on DE (guide:367). Still unmeasured: what happens when the packed groups do not fit the circumference, reachable on a small map with a large `base_size`. Also emulate guide:857's bug: with multiple player lands under `grouped_by_team`, the additional land positions do not generate properly.
- `direct_placement` in <PLAYER_SETUP>: disables circular positioning; player lands with `land_position` go exactly there; assigned `create_land`s likewise (guide direct_placement).
- `land_percent P` on player lands: total-map percentage **divided equally among players**; `number_of_tiles N`: N **per player** (guide).

**`assign_to` — the command Sec.3.1 borrows its teams vocabulary from, modelled here rather than left as a trailing clause.** Sec.3.1 sources "0 means un-teamed" from this entry, so the rest of the entry is in scope and it decides object placement, not just a field on a land record: `set_place_for_every_player` iterates "player lands **or lands assigned to players**" (guide:2263), so a mis-modelled `assign_to` moves S6 objects. Signature is `assign_to AssignTarget Number Mode Flags` (guide:994–1012):

- **`AT_PLAYER n`** (1–8, lobby order) and **`AT_PLAYER`'s sibling `AT_COLOR n`** (1–8, player colour): the land belongs to that player. **Modelled.** `AT_COLOR` resolves to the same player as `AT_PLAYER` for us, because the preview has no colour assignment — one `notSimulated` note per command saying so, since on a real lobby the two differ.
- **`AT_TEAM n`**, domain `(-10, -4, -3, -2, -1, 0, 1, 2, 3, 4)`, **canonical** team numbers per Sec.3.1, never the picker's. Positive `n` gives the land to *a* player from team `n`; `0` targets an un-teamed player; **negative `n` targets a player NOT on team `|n|`** (guide:1002); **`-10` gives the land to any player** (guide:1003). Not the whole team — one player.
- **`Mode`** (`-1` or `0`, guide:1005–1007, "only matters for AT_TEAM"): `0` selects that player at random, `-1` selects in lobby order. **Modelled** — `-1` is deterministic and free, `0` draws from the S1 substream.
- **`Flags`** (0–3, guide:1008–1012): `1` resets players already assigned before starting, `2` means do not remember this assignment, `3` is both. **Not modelled in v1** — it changes which player a *later* `assign_to` picks, and no corpus map exercises it. One `notSimulated` note when a non-zero flag is present.
- **Lands assigned to players who are not playing are not created** (guide:1015) — already stated below, repeated here because this is where the reader looks.
- **`land_position` is IGNORED on an assigned land** (guide:1016: "All lands belonging to players will be in a circle and land_position will be ignored, unless direct_placement is specified in `<PLAYER_SETUP>`"). This overrides the neutral-land origin rule immediately below: an assigned `create_land` takes a **ring slot**, like a player land, and only `direct_placement` restores its `land_position`. Getting this backwards puts every assigned land at its written coordinates on a map where the engine puts it on the circle, which is a whole-layout error rather than a detail.

If only `AT_PLAYER`/`AT_COLOR` were modelled and the rest emitted `notSimulated`, that would be a legitimate v1 answer too — but it has to be one or the other in writing, and the above is cheap enough that there is no reason to take the smaller one.

**Neutral lands** (`create_land`, unassigned — for assigned ones see `assign_to` above): origin =

1. `land_position` if present (ignores borders; if outside borders, the land will not grow past base_size — emulate).
2. Else a rejection-sampled random tile: inside borders, inside the **cross-shaped area** (not corners) unless `generate_mode 1` — reject candidates where *both* |x−center| and |y−center| exceed **0.35·(half the reference span)**. **The centre and the span are those of the rectangle the BORDERS leave, not of the map — MEASURED (RMSTEST_51, 2026-08-11, BUG-009, applied 2026-08-12).** With no borders the two frames coincide and this is the map's own centre with span `dim`, i.e. **0.171·dim**, which is what the original measurement below says; with borders the cross moves and shrinks with the box, and the map-frame reading left a bordered land drawing its origin from an L-shaped sliver along the box's outer edges. Each axis takes its own span, which is a judgment call: RMSTEST_51's box is square and cannot separate that from one reference length taken off a single axis. **MEASURED (RMSTEST_25, 2026-08-01), and the reference length was the error, not the constant.** 258 origins over six runs put **zero** in the modelled corner region against ~23 for a uniform draw, so the cross is real; but the observed maximum of `min(|dx|,|dy|)` was **20.5 tiles on a 120 map**, with eleven of the twelve corner-most samples sitting at *exactly* 20.5 — a hard wall, not a distribution tail. 20.5 is 0.342·(dim/2). Revisions 3 through 6 applied 0.35 to `dim`, which draws a cross **twice the engine's width** and scatters origins through a band the engine never uses. The high inter-origin merge rate in that test independently corroborates a smaller placement region. Symmetry control passed (mean x 0.4958, mean y 0.4924); at least `base_size` from every edge; at least `min_placement_distance` (center-to-center; default: `other_zone_avoidance_distance` edge-to-edge) from prior origins. **K = 100 [tune]** attempts; on exhaustion, the engine places the land **at map center, overlapping whatever is there** — we do the same and record `originFallbackCenter` (Sec.7), which is exactly the signal 5.2 wants.

**Origin stamp:** square of radius `base_size` (default 3 → 7×7), or inscribed circle if `set_circular_base`. Origins may overlap; later stamps overwrite (guide: "the land placed last will be the one visible").

**Terrain painting — stated explicitly since 2026-08-07, because leaving it implicit cost a release.** After growth, every tile a land owns takes that land's `terrain_type` in `grid.terrain`. This was never written down here: the section describes lands claiming tiles and the renderer reads `grid.terrain`, and the step between the two was assumed rather than specified. The implementation duly wrote `landId` and `zone` and never touched `terrain`, so **every map generated as one flat `base_terrain`** and every downstream stage — `create_terrain`'s `base_terrain` matching, the water mask, object habitats, connection costs — matched against a grid with no terrain on it. A single corpus map reported 19,608 placement failures that were all this one omission, each of them a true statement about the grid it had been handed.

Ordering, since three things write `grid.terrain`: this runs after growth (a land covers its final footprint, not its origin stamp) and therefore before S4, whose patches paint *on top of* land terrain — which is the whole reason `base_terrain` matching has anything to match. Within S1 later lands overwrite earlier ones for free: `grid.landId` has already resolved every overlap, so each tile is painted exactly once, by whichever land holds it. A land whose `terrain_type` is absent or unresolvable paints nothing and leaves the base fill showing.

**Terrain references: three written forms, one resolver.** A terrain slot anywhere in the language (`terrain_type`, `base_terrain`, `base_layer`, `beach_terrain`, `terrain_to_place_on`, `replace_terrain`, `terrain_cost`, …) may be written as **a built-in constant**, **a bare id** (`terrain_type 26`), or **a name the script defines itself** (`#const WOODIES 48`). The last two are not edge cases: only 78 of DE's 131 terrains have a callable constant at all, so a bare id or a `#const` is the *only* way to reach the other 53, and shipped maps use both heavily. Resolve all three in one place, in this order:

1. a number is the id, and an id absent from reference data still resolves (CLAUDE.md's positive-resolver rule — our not knowing a terrain is not evidence the game lacks it);
2. `game-constants.json` by `rmsConstant`;
3. the script's own numeric `#const` table.

**Order 2-before-3 is normative, not incidental**: the engine loads `random_map.def` before the script and `#const` is first-definition-wins, so a script redefining `WATER` does not take effect in game and must not take effect in the preview. Only a string matching none of the three is a genuine "reference data doesn't know this terrain".

**Zones:** player land → zone **`playerNumber − 10` with `playerNumber ∈ [1, N]`**, so player 1 is zone **−9** and no player collides with `create_land`'s shared default of −10 (guide:1038, confirmed by guide:1074's "player 1 … using their default zone of −9"). Rev 3 wrote "player land i → zone i − 10", which under the 0-based `i` an implementer would naturally use puts player 1 in −10, silently merging every player land with every neutral land. `create_land` default → zone −10 (shared); `zone N` explicit; `set_zone_by_team` → **team zone is `TeamNumber − 9`, team 1 in −8** (guide:1056), where `TeamNumber` is the **canonical** team from Sec.3.1, never the picker's selected number. So every member of canonical team 1 shares zone −8, team 2 shares −7, and their lands can grow together — which is what makes Team Islands render as team islands. Stated rather than left to derivation for the same reason the −9/−10 trap above is stated.
  **Un-teamed players: MEASURED (RMSTEST_37, 2026-08-04, five runs). There is no special case — the formula simply applies.** An un-teamed player carries an **engine-internal team number of their own** (player `k` behaves as team `k`), so `set_zone_by_team` gives them zone **`k − 9`**: player 1 → −8, player 8 → −1. The occupied set is `{−8..−1}`, one higher than the same players' default zones.
  Evidence, with the control that the two earlier attempts lacked: with player 1 pinned by `direct_placement` and probe lands at fixed offsets, a probe at **`zone -8` made contact with player 1's land in all five runs (min distance 3, 1, 4, 3, 1)**, while a probe at `zone -9` and a `zone 5` control sat at **exactly 12 tiles in all five runs — identical to each other, and clearly separated**. Five distinct maps.
  **This overturns a pin made here on 2026-08-01, and the error is worth naming.** That revision reasoned that `TeamNumber 0` would compute to −9, collide with player 1's *default* zone, and collapse an FFA map into one landmass — so it pinned the "graceful" alternative of keeping `playerNumber − 10`. The premise was wrong: an un-teamed player is not team 0 for zoning purposes, they are their own team, so no collision was ever possible and nothing needed rescuing. **The literal reading of guide:1056 was right and the graceful-degradation instinct overrode it.** Note the rev-6 text this replaced already said "player `k` gets zone `k − 9`" and was correct.
  **Do not confuse this with the label vocabulary.** `TEAMn_SIZEm`/`PLAYERx_TEAMy` place a lone player in **team 0** (Sec.3.1's ≥2-members rule, which is separately evidenced by the reachable-set match). Zones and labels genuinely disagree about solo players: the labels report what the *lobby* sees, the zone is an internal land-growth property. Both are now measured and both stand.
  Also emulate guide:1055's footgun: `set_zone_by_team` on a `create_land` assigns that land to **player 1's team zone** no matter whose land it is, which is a clean `validate()` hook for a construct the guide calls not recommended. Note that under real teams this is now player 1's *canonical team* zone, so it merges the land with player 1's whole team rather than with player 1 alone. `set_zone_randomly` → uniform in [−8, playerCount−9] (guide:1071 states the range directly); zone −12 → belongs to no zone (other zones may grow over it).

**Size targets:** `land_percent` → `P/100 · dim²` tiles (per-player division applied first); `number_of_tiles` → N. behavior_version 0: target is *additive* to the origin square; version 1/2: origin square *included* in the target (guide behavior_version). Default when neither given: land_percent 100.

**Out-of-range values that shipped maps actually use — pinned, because these are discovered otherwise.** `de-official-map-issues.md:290` records DE-official scripts writing values outside the documented ranges, and the documented range is not the accepted range. **Do not clamp `land_percent`**: `Crownwood.rms:173` writes `land_percent 1024` and `fortified_clearing.rms` writes `128` four times, against a documented 0–100. Compute the target as written, so 1024 asks for ten times the map, the land runs to frontier exhaustion, and it reports `growthShortfall` with `blocker: space`. That is the honest outcome and it is also probably what the engine does (these read as saturating idioms — "as big as it can get"), but it is a *consequence* of not clamping rather than a measured behaviour, so treat a preview that renders Crownwood's land filling the map as correct-until-measured. **Do clamp `land_position`**: `Michi.rms` writes `land_position 100 100` at three sites against a documented 0–99, and Sec.4's `round(X/100 · dim)` at `X = 100` yields exactly `dim`, which is off-grid for `x ∈ [0, dim)`. Clamp the converted tile to `[0, dim − 1]` after rounding, not the percentage before it.

**Connectedness is a function of `clumping_factor`, and the frontier model survives with one bucket changed. MEASURED (RMSTEST_38, 2026-08-04, five distinct maps, six `cf` values on one map).** A single `create_land` does *not* always come back in one piece — but whether it does is governed entirely by `clumping_factor`:

| `clumping_factor` | −20 | 0 | 8 (default) | 20 | 40 | 100 |
|---|---|---|---|---|---|---|
| 4-connected pieces | 6–10 | 1–5 | 1–2 | **1** | **1** | **1** |
| circularity of largest piece | 0.133 | 0.181 | 0.360 | 0.409 | 0.428 | 0.463 |
| tiles against a declared 400 | **−6.5%** | +4.6% | +3.3% | +3.2% | +3.6% | +4.1% |

**Piece count falls monotonically and reaches a hard 1 by `cf 20`**, which is inside the corpus's own common band (15–25) — so ordinary maps never see this and the effect is confined to the low end. Identical under 8-connectivity, so the pieces are genuinely disconnected rather than a diagonal snake split by the probe's 4-connectivity.

**Normative model:** `clumping_factor` sets how strongly growth prefers candidates adjacent to the land's existing mass. Above ~20 growth is pure frontier expansion exactly as described below. Below ~20 a land's turn may instead place a tile **detached from its existing mass**, seeding a new component, with the probability rising as `cf` falls. **So the weight-bucket machinery, the guide:927 regimes and the round-robin turn structure all stand; what changes is that a turn has a second, rarer source of candidates.** This is the cheap repair, and the expensive alternative (growth is not frontier-based at any setting) is refuted by `cf ≥ 20` giving exactly one piece in fifteen consecutive land generations.

**Where the detached tile comes from — this is the part that has to be specified, and it is not the weight.** Rev 6 wrote the repair as "bucket index 0 exists", weighted by `neighborsOwned = 0`. That does not implement: the frontier is *defined* as candidates 4-adjacent to owned tiles, so every candidate in it has `neighborsOwned ≥ 1` and a bucket 0 keyed off that count is unreachable by construction. An implementer following the growth paragraph below would have produced the pre-repair model and never seen the `cf −20` fragmentation at all. The weight is also the fittable half; the **candidate source** is the modelling choice, and leaving that open is leaving the wrong thing open.

**Normative form.** At land start, sample a small **detached-seed reservoir** of `R` **[tune]** tiles — rejection-sampled by the same origin rules the land's own origin used (inside borders, inside the cross unless `generate_mode 1`, not owned) — and hold it alongside the frontier. Each turn, with probability `w(cf)` **[tune]**, the land draws from the reservoir instead of the frontier; the drawn tile is claimed and its empty 4-neighbours enter the normal weight buckets, so the new component grows by the ordinary rule from then on. `w(cf)` is 0 at `cf ≥ 20` and rises as `cf` falls, fitted against the piece counts in the table above (6–10 at `cf −20`, 1–5 at 0, 1–2 at 8). Reservoir draws are O(1) and the reservoir is a fixed-size `Int32Array`, so **Sec.11's frontier structure and its 40 ms budget are untouched** — which a bucket whose candidate set is "every unowned tile" would not be, since that is a scan.

Two properties this form is chosen to preserve, both from the RMSTEST_38 measurement: piece sizes at `cf −20` were **comparable rather than one-large-plus-crumbs** (a reservoir sampled once at land start, with every seed then growing in the same round-robin, reproduces that; seeding lazily on demand does not), and fragmentation is a function of `cf` alone with no dependence on land size or map size. **Both `R` and `w(cf)` are `[tune]` and the *form* is a modelling choice, not a measurement** — what is measured is the piece-count column, and any mechanism reproducing it is admissible. Tracked as Sec.15 item 18.

**A second finding, and it is separate from connectedness: at `cf −20` growth does not meet its budget.** Every other setting overshoots by the familiar +3 to +4.6% (Sec.4's growth overshoot); `cf −20` comes in **6.5% short**, 374 tiles against 400, and one run reached only 340. A land scattering into ten fragments evidently exhausts its placement attempts before spending its budget. Model it as a real shortfall and report `growthShortfall` (Sec.7) rather than silently truncating.

**`clumping_factor 100` is accepted and is not clamped**, which matters because **17 uses across the 32 tracked maps write exactly that** (18 counting `test-maps/local/`) and community sources give the maximum as 99. It produced one piece in every run with the highest circularity in the sweep — though the 20 → 100 circularity rise (0.409 → 0.463) sits inside the run-to-run spread, so treat "more circular than `cf 20`" as unproven and "accepted, behaves like a high value" as measured. Consistent with RMSTEST_20/21's finding that circularity saturates near 15–20.

**Growth — synchronized frontier expansion:** all lands grow in round-robin turns, one tile per unfinished land per round (this approximates "growth happens all at once"). Per turn, a land draws from the detached-seed reservoir with probability `w(cf)` (above), and otherwise samples from its frontier (empty candidates 4-adjacent to owned tiles) by weight. The frontier is held in **integer weight buckets** (Sec.11) — bucket index is a function of `neighborsOwned ∈ [1,4]` and the land's clumping regime, sampling is O(1), and no `Math.pow` is involved (goal 5). The `[1,4]` range is exhaustive *for the frontier*, which is why fragmentation needs the reservoir and not a fifth bucket. Regimes follow guide:927, minus its 40+ row:

| `clumping_factor` | Guide:927 | Model |
|---|---|---|
| negative | "extremely snakey, generally not recommended" | strongly favour `neighborsOwned == 1` |
| 0 and above | "more irregular lands" → "rounder lands" | weight rises **continuously** with `neighborsOwned`, steepness ramping with `cf` and saturating by `cf ≈ 15` |

**MEASURED (RMSTEST_21, 2026-08-01), and this replaces a four-row table with two rows.** Two things were wrong:

**The 40+ directional regime does not exist.** Six lands of 600 tiles at `cf` −5/0/8/25/40/60, one per regime:

| `cf` | circularity | bbox aspect |
|---|---|---|
| 8 | 0.265 | 1.50 |
| 25 | 0.391 | 1.38 |
| 40 | 0.384 | 1.24 |
| 60 | **0.394** | **1.05** |

`cf 60` came back the **roundest and least elongated** land of the six, and 40 and 60 are indistinguishable from 25. Rev 3 through rev 6 modelled it as a per-land preferred direction with weight rising on the projection onto it — an invention built on one guide sentence, and it would have drawn peninsulas the engine never draws. Deleted.

**The regime boundaries are not steps.** Circularity ramps smoothly with no discontinuity at the guide's stated boundaries (see Sec.6.4's terrain table, measured the same day, where the ramp is clearest). Rev 4's warning against collapsing to a monotonic weight was aimed at preserving the 40+ peninsula; with that regime gone the warning inverts, and **a continuous weight is now the closer model**. Only the negative case stays special, and it is dramatic rather than marginal.

Default 8 for lands (guide:925). A candidate is rejected if:

- **outside a border.** `border_fuzziness` is an *adherence* percentage `f` (default 20; guide:903). **MEASURED (RMSTEST_23, 2026-08-01): `f = 0` switches the border off entirely, and any `f > 0` is very nearly a hard stop.** Six runs on a 200 map with the border at tile 80 and a land pressing hard against it from tile 90:

  | `f` | min x per run | mean penetration |
  |---|---|---|
  | 0 | 63, 57, 66, 66, 81, 60 | **14.5 tiles** |
  | 20 | 78, 78, 78, 78, 81, 81 | **1.0** |
  | 50 | 79, 79, 80, 79, 79, 79 | **0.8** |
  | 100 | 80, 80, 80, 80, 80, 81 | **−0.2** |

  **Normative form: reject any candidate beyond the border when `f > 0`, except for a single fringe tile accepted with probability ≈ `(100−f)/100`.** That reproduces 1.0 at the default and 0.8 at 50 without an unbounded tail. `f = 0` → always accepted (borders ignored); `f = 100` or negative → `d ≥ 1` never accepted. **`f = 100` stopped on exactly tile 80 in five of six runs, so Sec.4's border tile arithmetic is right to the tile** — the cleanest single reading in the batch, since it is a hard boundary rather than a distribution.

  Both prior models are dead, and they erred in the same direction. Rev 3's single depth-independent Bernoulli accepts 80% of the first ring *and* 80% of the ring beyond, dissolving the border. Rev 4 corrected it to `d` independent Bernoulli(`f`/100) rolls, geometric decay with a mean of a few tiles — closer, and still far too permissive: over an edge this long that model reaches depth 4+ nearly every run, against a measured 1. The lesson is not the constant. **Two rounds of reasoning about the shape of a distribution moved the answer in the right direction and stopped well short of it, and one map settled it.** The closed form `((100−f)/100)^d` is retained here only as the historical model, and Sec.8's ban on `Math.pow`/`**` no longer bears on the implementation at all, since the rule is now a single roll;
- within `other_zone_avoidance_distance` (the **smaller** of the two lands' values — guide) of a tile owned by a different zone (zone −12 exempt);
- already owned.

A land stops at target, or when its frontier is exhausted — recording a `growthShortfall` report (owned/target, dominant blocker among border/zone/space) for 5.2's land layer. `land_conformity` is **not simulated** (buggy in-engine, guide advises avoiding it) — SimulationNote when present.

`base_elevation H`: after growth, set `elevation = H` on the land's tiles — **skipped for lands with a water terrain_type** (guide:959: doesn't work in HD/DE) (requires <ELEVATION_GENERATION> present in-engine, empty is enough — guide:952; if absent, note it — validate() territory but cheap to flag here too). **Clamp `H` before it reaches the grid: negative values maximally elevate a land** (guide:957), so `H < 0` → 16, and `H` above 16 → 16. This is not pedantry about an unlikely value — `elevation` is a `Uint8Array` (Sec.4), so an unclamped `H = −1` stores 255 and the renderer's brightness shading (Sec.2) draws that land blinding white. Documented range is 1–16, default 0 = not elevated (guide:954). **The clamp value is CONFIRMED in-game** (Test 4, 2026-07-30): three patches at `base_elevation` −1, 7 and 16 side by side, and the −1 patch matched the 16 patch exactly. "Maximally" resolves to 16, not to some higher internal cap.
    **The `<ELEVATION_GENERATION>` requirement is more serious than a note.** The section may be empty, and its mere presence is enough (guide:952, confirmed by the same test). But *without* it the map still generates looking normal, while base-elevation slopes silently fail and **the game crashes when the map is played** (reported by the guide's author in public Discord; the crash itself is second-hand and not reproduced here). So this is an error-severity `validate()` check, not a preview note — a silent authoring mistake that ships a crashing map. Tracked in CLAUDE.md. `land_id`, `assign_to_player`/`assign_to` recorded on the land record for S6 (lands assigned to non-playing players are **not created** — guide).

### 6.2 Elevation (S2)

Per `create_elevation MaxHeight { … }` command:

- Tile budget `number_of_tiles` — default **`120 × dim/120`, i.e. simply `dim`** — **MEASURED, and it is NOT area-scaled** (RMSTEST_14, 2026-07-31). The guide's "about 120 on tiny maps" (guide:1228) scales with the map's **side length**, not its area. Measured level-1 tile counts: Tiny 126/128, Small 147/158 — a ratio of **1.20**, which is 144/120. Area scaling would have given 1.44. Revisions 2 through 6 of this doc all modelled it as `120 × dim²/14400`; that is wrong and the error compounds with size, predicting 1920 default tiles on Ludicrous where the real answer is 480. Note the raw counts sit ~6% above the budget at these sizes, consistent with the growth overshoot of Sec.4 (which measured ~3% at a budget of 829 — the overshoot fraction is larger for small budgets). Note the form: rev 4's `86 × area-ratio` was back-derived by dividing 120 by the guide's rounded 1.4 ratio, which is the exact display column Sec.4 spends a paragraph banning for scaling on determinism grounds. Same arithmetic, no rounded constant. Clump count `number_of_clumps` (default 1); `set_scale_by_size` scales tiles, `set_scale_by_groups` scales clumps (DE-fixed semantics; only the *last* scale attribute applies — guide:1257/1274); budget divided equally among clumps. **The overshoot below is per clump, not per command, and grows sharply as the per-clump share shrinks** — RMSTEST_22a asked for 2000 tiles across 500 clumps, 4 each, and delivered ~3080, **54% over**, or 6.2 tiles per clump. Against the ~3% measured for a single 829-tile clump, that puts a floor of roughly 6 tiles on a clump regardless of its share. Model it as `max(6, share)` before growth rather than as a percentage.
- Clump seeds: random eligible tiles — terrain matches `base_terrain` (+`base_layer` if the map used one), **≥9 tiles from every player-land origin** (guide: "elevation avoids the origins of player lands by about 9 tiles").

  **Seed placement is biased toward the `y − x` diagonal, and the bias is WEAK. MEASURED DIRECTLY (RMSTEST_39, 2026-08-04):** 560 seeds over six runs, recovered as connected components at the 6-tile clump floor with ~94 components per declared 100, so each component is one seed. The favoured:disfavoured split of seed positions is **1.31 : 1**. The axis is the `y − x` diagonal, not `+y`, because DE renders the map rotated 45° (unchanged from the rev-6 finding; the failed `mean x` control is what caught it).

  > ⚠ **THE "STEP WITH WEIGHT 18 vs 1" MODEL IS WITHDRAWN.** Every figure that model rested on — 18:1, 20:1, 12:1 balanced, 7.16:1, the 29:1 interior reading — was measured from *elevated tiles*, which are seeds seen through growth and through heavy component merging. None of them is a seeding weight. The direct seed measurement is 1.31:1.

  **The observed TILE ratio is not an engine constant. It scales with CLUMP DENSITY.** On a 200 map, holding the per-clump budget at the 6-tile floor:

  | clumps | 50 | 100 | 250 | 500 | 1000 |
  |---|---|---|---|---|---|
  | tile ratio | 1.45 | 1.88 | 3.74 | 7.01 | 14.88 |

  Above ~250 clumps this is proportional: `ratio ≈ 585 × (clumps / mapArea)`, i.e. **`clumps / 67` on a 200 map [tune]**, with ratio/density measuring 598, 561, 595 across the three highest points. Below ~250 it flattens toward the seed-bias floor of 1.3–1.9. **The per-clump budget is irrelevant**: 500 clumps at 6 tiles gives 7.01 against 500 clumps at 4 tiles giving 7.16, a 2% difference across a 50% budget change and 46% more coverage.

  **Normative form for 4.3.** Draw seeds with a weight ratio of **1.3 : 1** favouring `y > x`, uniform with respect to distance from the map edge. Do **not** apply a border rule and do **not** apply a per-band weight table.

  **The density amplification, and read this carefully because rev 6 stated it in a way that cannot be implemented and that repeats the mistake item 11 cost six sittings to find.** The five-row table above is a measurement of **tiles**, not of seeds. Instructing 4.3 to "fit a weighting on seed selection to the table" asks it to fit a *seed* parameter against a *tile* observation — which is precisely the seeds-seen-through-growth-and-merging convolution that produced 18:1, 20:1 and 29:1 and made every one of them wrong. Our generator has its own growth and its own merging, and they are not the engine's, so a seed weight of 7:1 at 500 clumps will not produce a tile ratio of 7.01 in our renderer.

  So the fit targets the **output**, not the parameter:

  ```
  seedRatio(clumps, mapArea) = clamp( 1.3 + A · max(0, density − d0) , 1.3, RMAX )
      where density = clumps / mapArea,  d0 ≈ 250/40000,  A, RMAX [tune]
  ```

  - **Below the knee** (`density ≤ d0`, i.e. ~250 clumps on a 200 map) the ratio is the seed-bias floor, 1.3. The table's low rows (1.45 at 50 clumps, 1.88 at 100) are *tile* ratios at that floor and must not be read as seed weights.
  - **Above the knee** it rises with density. `A` is fitted so the generator's own **tile** ratio reproduces the five table rows — run the generator, count elevated tiles either side of the diagonal, compare. That makes the table an **acceptance test** (Sec.13) rather than a parameter table, and it is the only formulation where "the constant is right" means anything.
  - **`RMAX` is a real clamp and is not optional.** The relationship is linear in density with no measured upper end, so a dense script on a small map — 2000 clumps on Tiny is `density` 0.139, ratio ≈ 82 — otherwise computes an unbounded weight and empties the disfavoured half. The measured range tops out at 14.88; clamp at **20 [tune]** and emit nothing (this is a modelling bound, not an authoring error).
  - **Between the table's points, interpolate on the formula, not on the table.** The five rows are not a lookup.

  This is `[tune]` in `A` and `RMAX` and `[verify]` in shape — the knee is read off five points and the mechanism behind the density scaling is still unknown (below). Tracked as Sec.15 item 20.

  **Five hypotheses were tested and rejected. Do not re-tread them** (full evidence in `docs/elevation-bias-study.md`):

  | hypothesis | refuted by |
  |---|---|
  | biased clump *growth* | clump-size ratio flat at 1.16 / 1.13 across a 4× budget change (RMSTEST_40a/40b) |
  | ratio tracks *coverage* | 3.29% cover → 1.41 against 1.55% cover → 1.88; not monotone |
  | ratio depends on *map size* | RMSTEST_22a and 35 are the same script at two sizes; the difference is clump density |
  | seeds excluded from a border band | component centroids occur at edge distance 0, and are more numerous near edges |
  | clumps spilling across the diagonal | only 0.7–3.0% of disfavoured tiles lie in a component that also holds favoured tiles |

  **`enable_balanced_elevation` barely changes the tile ratio**: 12.86 unbalanced against 12.27 balanced on identical scripts at identical coverage, a 5% reduction. The previously recorded 20:1 → 12:1 softening is withdrawn. Model it as a small reduction of the seed bias `[tune]`, not as a second weight table.

  **Player lands reduce the ratio substantially**, 7.16 → 2.24 on the same script and size (RMSTEST_35 against RMSTEST_32). The `≥9 tiles from player origins` exclusion and the diagonal bias therefore do not compose independently, and Sec.6.2 must state them together.

  **The mechanism behind the density scaling is unknown.** More clumps competing under `spacing 1` would naively push overflow into the disfavoured half and *lower* the ratio; it does the opposite. Two mechanistic hypotheses have already failed here, so the density relationship is recorded as empirical and predictive rather than explained.

- Grow each clump like a land region (clumping weight fixed moderate [tune]) to its tile share. **Measured engine behaviour: the clump overshoots its target by ~3%, with real run-to-run spread** — a budget of 829 produced 863, 855, 851, 848 across four runs (mean 854.25, spread 15 tiles ≈ 1.8%). Our growth stops exactly at target, so it under-produces against the engine by that margin. **Implementing the overshoot is optional and low priority [tune]**: 3% is invisible at preview scale and well inside Sec.13's statistical tolerances, so a plain stop-at-target is defensible. The number is recorded because it is *measured*, and because the spread matters more than the bias — 5.2's Monte Carlo should not expect elevation coverage to be repeatable to the tile.
- Height assignment: per clump roll target height `h ∈ [1, MaxHeight]` (single-clump commands always attempt MaxHeight — guide); tile height = `min(h, floor(distanceFromClumpEdge / spacing))` with `spacing` default 1 — concentric rings, wider flats for larger spacing.

  **`MaxHeight` is an ABSOLUTE CEILING and nothing adds — CORRECTED 2026-08-07, replacing "heights add on top of `base_elevation` (DE-relative behavior)".** A command raises a tile toward `MaxHeight`, never past it, and never lowers one already higher: `elevation[t] = max(elevation[t], ring)`. The distinguishing case, which is what settles it: two lands under ONE `create_elevation 6`, one sitting at `base_elevation 5` and one at 2, **both top out at 6** — the first shows shallow hills (5 → 6), the second tall ones (2 → 6). The withdrawn additive reading puts them at 11 and 8.

  Neither clumps within a command, nor commands within a section, nor `base_elevation` underneath are summed. `AD4 - Pag - v1.2.rms` is what exposed it: five repetitions of `create_elevation 7 { number_of_tiles 230400 }` over one region (230,400 tiles on a 40,000-tile map, so each floods all of it) plus a 180-clump `create_elevation 2` summed to 37 and clamped, putting **36,877 of 40,000 tiles at the ceiling of 16** on a map asking for 7. Repeating a command is the coverage idiom every script uses for `create_terrain`, not a height multiplier. Sec.15 item 25 has the run that confirms it.
- Misses (no eligible seed tiles) → `terrainAbsent` or `playerOriginAvoidance` failure reasons.

### 6.3 Cliffs (S3)

Coarse simulation — enough for layout honesty, no fine geometry (PLAN.md defers cliff fidelity; 5.2 defers cliff checking):

- Section present (even empty) → cliffs generate with defaults (guide: "simply typing the section header will generate default cliffs").
- Count = uniform `[min_number_of_cliffs, max_number_of_cliffs)` (min 3/max 8 defaults; max exclusive per guide:1351). Length in segments uniform `[min,max]` inclusive (defaults 5/9); tiles ≈ `3·(len+1)` (guide:1365: 3→12, 4→15, 5→18). **min > max crashes the engine** (guide:1363) — the preview must still not throw (goal 3), so treat it as zero cliffs plus a note that says the real game would crash.

- **A length below 3 draws nothing, PER CLIFF** (guide:1366, "minimum must be at least 3 for cliffs to appear") — roll each cliff's length in `[min, max]` and drop the rolls below 3. **Not a clamp, and not a section gate — MEASURED, `RMSTEST_45a/45b/45c`, two runs per arm, twenty cliffs requested (item 17b, BUG-008, applied 2026-08-12):** `min 2 / max 2` → **0** cliff units, `min 3 / max 3` → **66**, `min 2 / max 4` → **36**. A section gate predicts 0 in the third arm; a clamp predicts the first two matching; neither survives. The zero case is still produced, by every roll dying, which is why the guide's sentence reads true on the maps that write `min 1` or `2` with a max also below 3. **Do not fit a rate from 36-against-66**: cliff UNITS are not cliff COUNT, so that ratio conflates yield with length, and a rate needs `--clusters` component counts. The note now distinguishes "this section produces no cliffs at all" (max also below 3) from "fewer cliffs than it asks for".

  **The corpus reading, and it points the same way — recorded because a rev-7 draft briefly read it backwards.** Three **live, unconditional** sub-3 declarations sit in the corpus (`test-maps/local/Fortress.rms:748` — `min 2`, `max 4`, asking for 5–10 cliffs; `test-maps/QS_Three_Bays_v1.1.rms:465`; `test-maps/local/lombardia.rms2:355`), and `de-official-map-issues.md:290` records **six** DE-official maps doing it. That looked like a refutation — surely six official maps do not all have dead cliff sections — and it is not one. Under the rule those sections simply produce nothing, which is a perfectly ordinary outcome for a copy-pasted block nobody re-checked, and **`Fortress.rms` is the case that decides it**: it requests 5–10 cliffs at length 2–4, and Fortress is not a map anyone remembers having cliffs. It is known for its starting stone walls, castle and towers. So the best available observation on the most-played script in the list is *consistent with the rule*, not against it.

  **The draft that got this wrong is worth one sentence, because the error is reusable.** It described Fortress as "a map whose entire identity is cliff-walled player bases" — a claim inherited from a review and never checked against the game or the script. That single false premise inverted a finding: it turned "six maps have dead cliff sections, as documented" into "the spec renders a famous map wrong", and on the strength of it the rule was withdrawn, an interim per-draw model invented, and `language.json`'s bound widened. **Check the claim about the artefact before building an argument on the artefact.** A map's reputation is an observable and it was available for the asking.

  **Second-order: `language.json` keeps `min_length_of_cliff.min: 3`, and this is NOT the `circle_radius 0` / `base_elevation 0` class.** `RMS0203` does fire on the three live corpus uses, and that is a **true positive** — it tells the author their cliff section does nothing, which is exactly the beginner-mistake surfacing this project exists to do. The distinction that was briefly missed: `circle_radius 0` and `base_elevation 0` are documented as **functional** (0 disables circular placement; 0 means not-elevated), so warning on them was wrong; a sub-3 cliff length is documented as **non-functional**, so warning on it is the point. *A documented range is not an accepted range* cuts both ways, and "shipped scripts use it" is not by itself evidence that it works — six scripts using an inert value is six scripts with an inert section. The bound was widened to 1 on 2026-08-05 and **reverted the same day**; the entry's `notes` now say so, so nobody re-derives the same wrong fix.

  **The run that settles it (item 17b), unchanged and still cheap:** `min 2 / max 2` against `3`/`3` against `2`/`4`, same map, count cliff tiles. The discriminating map to look at first is **`Cliffbound.rms:2348`**, which is on the sub-3 list and whose name claims cliffs — if Cliffbound visibly has them, the rule is wrong and this whole paragraph goes with it.
- Each cliff: random walk of `len` 3-tile segments **from a 3-tile starting stub**, which is where the `+1` in the tile formula comes from — rev 3 wrote "a random walk of 3-tile segments" alongside `3·(len+1)` and the two disagreed by one segment. Direction change chance = `cliff_curliness`% (default 36) per segment. Start tiles: ≥22 tiles from every land origin, not on water, **not on sloped tiles** (cliffs "avoid any slopes" — guide; S2 elevation is already available at S3), ≥`min_distance_cliffs`·3 tiles from existing cliff tiles (default 2), ≥`min_terrain_distance`·3 tiles from water (default 2) (guide values). Walk steps that would violate constraints truncate the cliff (guide: "may end up shorter").
- Marks `cliff` mask; renderer draws cliff glyphs. The engine's under-cliff terrain-16 mechanics are **not simulated** (Sec.9).

### 6.4 Terrains (S4)

Sequential per `create_terrain T { … }`, in script order (guide: "generated sequentially… positions cannot be directly specified"):

- Budget: `land_percent` (of total map) or `number_of_tiles` — default **`122 × dim/120`** — **MEASURED, side-length scaled, not area** (RMSTEST_14, 2026-07-31; guide:1616, "default:122 tiles on a tiny map"). Same correction as Sec.6.2 and the same measurement: DIRT tile counts of 120/121 on Tiny and 148/146 on Small, a ratio of **1.22** against 1.20 for side length and 1.44 for area. The fit is close to exact — `122 × dim/120` predicts 122 and 146.4 against measured 120.5 and 147. **Terrain growth also shows no overshoot**, unlike elevation: measured counts land on the budget rather than ~3-6% above it, so do not carry Sec.6.2's overshoot allowance across to terrains; `number_of_clumps` default 1; scaling per attribute — note the terrain-specific rule: `set_scale_by_groups` scales **both** clumps and tiles for terrains (guide), unlike elevation.
- Eligible tiles: **terrain == `base_terrain` AND (no `base_layer`, or layer == `base_layer`)**. **CORRECTED 2026-08-07, and this reverses a pin made in rev 4 — the two guide lines genuinely disagree, so the reason for preferring one is the whole of the argument.**
  - guide:1471, inside **`base_layer`'s own entry**, states the combination rule normatively and gives a worked example: "If used together with base_terrain, the new terrain will be placed only where **both** the base and the layer apply."
  - guide:1603 is an aside inside **`land_percent`'s** entry, explaining why `land_percent 100` does not fill the map: "terrain will only be replaced where the appropriate base_terrain **or** base_layer is present". It is not about combining the two attributes at all; the "or" is covering both attribute names in a sentence about something else.

  The dedicated entry wins, on this project's own "look for the sentence" discipline: 1471 is the sentence about combining them and 1603 is not. The disjunction also makes the attribute pointless — under OR, adding `base_layer` can only ever *widen* the eligible set, so "place this terrain on the desert that is layered over grass" matched every bare grass tile on the map. Rev 4's stated objection to the conjunction, that it "narrows the eligible set to the intersection", is exactly what the attribute is for. **Worth one RMSTEST** (Sec.15 item 24) since two guide lines conflict, but nothing about the conjunction reading is in tension with anything else measured. Within `height_limits` if given; ≥`spacing_to_other_terrain_types` from any tile of a *different* terrain (distance-transform query); **pinned approximation:** cliff tiles also count as foreign terrain for this spacing — the engine gets this via under-cliff terrain 16, which we don't simulate (Sec.9.7); ≥ each `spacing_to_specific_terrain T d` (accumulated list); `set_flat_terrain_only`: also ≥spacing from sloped tiles (only when spacing ≥1 — guide); `set_avoid_player_start_areas d` (default 13 when bare): ≥d from player origins with mild variance.
- Clump seeds from eligible set; grow restricted to eligible tiles, adjacent clumps merging naturally. **Terrains have their own `clumping_factor` regimes — do not reuse Sec.6.1's land table.** Guide:1646–1648 gives a different default, a different useful range, and different boundaries, and there is no directional regime at all:

  | `clumping_factor` (terrain) | Guide:1647–1648 | Model |
  |---|---|---|
  | negative | "extremely snakey" | strongly favour `neighborsOwned == 1` |
  | 0 to ~15 | "more irregular" (0–5) → "rounder terrain patches" (5–25) | weight rises **continuously** with `neighborsOwned`, steepness ramping with `cf` |
  | above ~15 | *still inside* the guide's range (useful 0–25, moderate 5–25) — the saturation is ours, measured | saturated; no further change, no directional streaking |

  Note the third row's guide column, since rev 6 had it wrong: guide:1647 gives the useful range as 0–25 and guide:1648 calls 5–25 moderate, so **15–25 is inside both**. The saturation at ~15 is RMSTEST_20's finding and it stands on its own; the guide does not corroborate it and must not be quoted as if it did.

  **MEASURED (RMSTEST_20, 2026-08-01).** Nine terrains, one clump each, identical 400-tile budgets, same map and same run so only `cf` differs:

  | `cf` | −5 | 0 | 3 | 5 | 8 | 15 | 20 | 25 | 40 |
  |---|---|---|---|---|---|---|---|---|---|
  | circularity | **0.035** | 0.068 | 0.128 | 0.172 | 0.217 | **0.272** | 0.222 | 0.217 | 0.268 |

  (Circularity is `4·π·area/perimeter²`, normalised so a disc is 1.0, a solid square 0.785 and a one-tile-wide snake tends to 0.)

  Two readings, and the first is the one that matters:

  **The bucket model is the wrong shape.** `cf` 0 → 15 is a smooth, near-linear ramp with **no step at the guide's stated 5 boundary**. RMSTEST_20's header recorded in advance that a smooth ramp would mean exactly this, so the prediction is not being fitted after the fact. Replace the buckets with a continuous weight whose steepness is a function of `cf`.

  **The saturation point is ~15, not 25.** Above 15 the values plateau in the 0.22–0.27 band and stop responding, so the clamp survives but sits lower than the guide's useful range suggests.

  Negative remains dramatically separate at 0.035 and keeps its own rule.

  Default **20** (guide:1646, "different than for lands"), which by this measurement is already in the saturated band — where the land default of 8 is mid-ramp. That difference between the two defaults is real and is why the tables stay separate even now that both are continuous. Rev 4 corrected the land table and left its terrain twin pointing at it, which was the same error one level down.
- `terrain_mask 1/2` — **two behaviours, and the difference is which terrain OWNS the tile, not how it is drawn (clarified 2026-08-07).** guide:1502-1509: mask 1's new terrain "is masked over the base terrain and inherits its properties", mask 2's "is masked under the base terrain and provides new properties", where "properties" is spelled out to include placement restrictions, automatic objects such as forest trees, and minimap colour. So:
  - **mask 1**: write the new terrain into `layer`; `terrain` keeps the base, and a later command's `base_terrain` still matches the tile.
  - **mask 2**: the new terrain takes `terrain` and the previous base moves into `layer`. A later `base_terrain` naming the old base no longer matches, and the tile's habitat and automatic-object behaviour change with it.

  guide:2486 gives the same direction from the object side: `layer_to_place_on` "works for terrain_mask 1, but not when set to 2 ... because the layer has become the main terrain". **An implementation collapsed both into "write to `layer`" on the reasoning that Sec.9 renders masking as a flat tint anyway, so the distinction would be invisible. It is not a rendering distinction at all**, and under that reading every mask-2 command was a no-op for the rest of the pipeline — `AD4 - Pag - v1.2.rms` uses mask 2 in two of its first three terrain commands. Only the visual BLEND is out of scope (Sec.9 item 6); which terrain owns the tile is not. Honesty note in Sec.9. `beach_terrain`: hand the terrain to the beach step that runs when this command finishes, scoped to the tiles this command claimed — the attribute picks the terrain, the step picks the tiles (see the beach subsection below). Skip it entirely if a <CONNECTION_GENERATION> section exists — the guide documents that bug; emulating it IS the honest choice, plus a note. Skipping the ATTRIBUTE is not skipping the beach: the coastline still takes the engine's own default, which is what the attribute would have been overriding.

**AUTOMATIC BEACHES ARE ENGINE BEHAVIOUR, NOT A COMMAND — added 2026-08-07.** Nothing in a script asks for them: the community DE terrain table states the rule on the beach terrains' own rows (id 2 BEACH "automatically placed when land terrains border water", id 37 ICYSHORE "created when snowy terrains border water"), and `beach_terrain` above exists to OVERRIDE it per command, which is why guide:1483 gives that attribute a default of BEACH. Without it a preview draws land meeting open water with no shoreline at all — 536 such tiles on `AD4 - Pag - v1.2.rms`.

Each **land** tile takes ITS OWN beach terrain (`beachTerrain` in `game-constants.json`, populated for all 131 rows) where it borders something deeper than itself; one tile wide, on the land side. The depth mask is taken before any write, so a new beach cannot make its neighbour look shallower than it was.

**THREE DEPTHS ARE READ, ONE BOUNDARY IS EDGED — corrected 2026-08-08, half of it withdrawn 2026-08-12 (BUG-010).** The map has land, **shallows** and open water. Sand appears where LAND meets either of the other two and **nowhere else**: `RMSTEST_52` put the three in a known order and counted 3 and 2 tiles on the shallows/open-water boundary against 336/312 and 30/90 on the other two, which is a triple junction rather than a rule. So a shallows band running out to sea comes out **sand, shallow, shallow, sea**, and the sentence below about edging every boundary between two depths applies to the landward one only. **The three-value mask still earns its place** — `isWater` alone calls `DLC_MANGROVESHALLOW` and the navigable ice family dry, so an `isWater`-only test leaves those coasts with no beach at all, which is the gap the depth model was introduced to close and which the landward half keeps closed. What the withdrawn half rested on: a `terrain_state` line about "thinner blending of shallows and beach terrain", read as evidence the two are adjacent by default when it describes an adjacency the author supplies. **A guide sentence that a construct CAN be configured is not a statement that the engine does it unasked.** Corpus effect of the withdrawal, measured at seed 7 on Normal: 6 of 32 maps change, total beach 8984 → 7577, the largest being `W4 - Immersion` 1752 → 1016 and `TL Tres Leches` 1045 → 678; one map gains a single tile through a downstream cascade.

Original text, for the shallows enumeration it carries: The map has land, **shallows** and open water, and the engine edges every boundary between two of them rather than only the outer one. Shallows are the terrain both land units and ships can cross — the community DE table's `Unit Pathing: all`, carried as `isHybrid` in `game-constants.json` — and there are ten of them: 4 SHALLOW, 26 Ice Navigable, 54 DLC_MANGROVESHALLOW, 55 DLC_MANGROVEFOREST, 59 DLC_NEWSHALLOW, 90 Forest Reeds (Shallows), 93 and 94 Moddable Walkable Shallows, 111 MUDDY_SHALLOW, 115 YELLOW_SHALLOW. The nine beach terrains and the five rice farms share that pathing value and are excluded: a beach is what the rule PRODUCES rather than a thing it edges, and a rice farm is not wet. So a shallows band running from a coast out to sea comes out **sand, shallow, sand, sea** — edged on both of its sides. Two of the ten are forests placed on shallows rather than shallows proper (55, 90); treating them as shallows is a flagged judgment call, on the grounds that both are named as growing out of a shallow rather than out of dry ground.

**`isHybrid` is ORTHOGONAL to `isWater` and deliberately does not replace it.** The two answer different questions and disagree in both directions. `isWater` is the placement question every other stage asks — can a building go here, does a cliff avoid it, is an object out of its habitat — and by that reading a shallow IS water. Depth is the question only this rule asks, and by that reading a shallow is neither land nor water: `DLC_MANGROVESHALLOW` is buildable, walkable ground that `isWater` correctly calls dry and the table still calls a shallow. Folding hybrid into `isWater` would have moved every consumer of the water mask, which is a far larger claim than this rule needs. All ten hybrid rows therefore also carry a `beachTerrain` — seven of them read `null` until this correction, and only because the first derivation pass read `isWater` and stopped.

Unlike `isWater` and `isForest`, `isHybrid` has **no name-heuristic fallback**: `YELLOW_SHALLOW` is a shallow and `YELLOW_SHALLOW_WATER` is open water, so no pattern separates them, and all 131 rows carry the field explicitly. A terrain the table has never covered falls back to `isWater`'s own answer, which leaves it behaving exactly as it did before the field existed.

Measured at seed 7 on Normal over the tracked corpus: nine maps change and the beach present when `<TERRAIN_GENERATION>` starts never decreases on any of them (`W4 - Immersion.rms` 1324 → 2468 final, `QS_Three_Bays_v1.1.rms` 2753 → 3700, `TL Tres Leches.rms` 376 → 1045). Two maps end with FEWER beach-family tiles than before (Pag 1364 → 1294, `Chaotic_Straitv0.99.rms` 4831 → 4805) and both are downstream cascade rather than lost coastline: Pag writes `create_terrain DLC_BEACH2 { base_terrain SHALLOW … }`, so shallows edged earlier are no longer SHALLOW for that command to convert, and its `<CONNECTION_GENERATION>` then replaces plain BEACH with DIRT where it would have left DLC_BEACH2 alone.

**WHEN IT RUNS — corrected 2026-08-07, having first shipped as a single pass after S5.** The beach step happens at the END OF LAND GENERATION and again at the end of every `create_terrain` command, so a beach exists for the whole of `<TERRAIN_GENERATION>` instead of appearing after it. The single late pass was refuted by the corpus rather than by argument: `base_terrain BEACH` has **67 uses across the tracked maps** (five consecutive in `AK_Namatjira.rms`, plus `DLC_WETBEACH`/`BEACH_BUILDABLE` variants elsewhere), and a beach that does not exist until after S5 matches none of them — those commands ran against an empty eligible pool and painted nothing, which reads as a quiet map rather than an error. Running late also made the pass the last writer on every coastal tile, so it silently undid the conversions those commands were for.

**EVERY run dresses the WHOLE grid, and the per-command step is UNCONDITIONAL — corrected 2026-08-08.** What is scoped to the painting command's own tiles is `beach_terrain` (guide:1483: "placed where the CURRENT terrain borders water"), not the step itself. The grid-wide part is load-bearing: a command that paints water puts land it never touched onto the coast, and only a grid-wide pass dresses that land.

An earlier version made the per-command step fire **only when the command set `beach_terrain`**, on the argument that an unconditional pass eats its own output — `create_terrain X { base_terrain BEACH }` converts the beach and the step converts X's waterline straight back, since X borders water and X's own row grows a BEACH. **The argument is sound and its conclusion was wrong, because it counted only the tiles that touch water.** Split the two cases:

- **A coast whose only beach IS the waterline.** The command converts that one-tile strip and the step converts it back, so the command is a no-op. That is the correct outcome, not a broken idiom: there was no beach anywhere else for it to act on.
- **A land made OF beach** (a beach clump, a `base_terrain BEACH` fill, a wide `DLC_WETBEACH` shelf). Every beach tile converts to X **except** the tiles touching water, which revert. The idiom does its work on the interior, which is the whole reason a script writes it.

So the unconditional step preserves the 67-use idiom rather than destroying it, and it also beaches the new coastline a command paints, which the conditional version left bare (measured at seed 7 on Normal: 873 unbeached coastal tiles on Pag, 829 on `24hr_Mont Saint Michel.rms`). The conditional reading protected the case where nothing was at stake and broke the case where something was. **What remains genuinely unmeasured is narrower than before — see Sec.15 item 28.**

`beach_terrain` is passed into the pass rather than acting on its own, so the attribute picks the terrain and the pass picks the tiles. That is what makes a NON-beach `beach_terrain` work (guide:1488 warns docks then cannot be built there, so the engine honours it), which a data-default-only pass would overwrite. A `beach_terrain` naming a WATER terrain instead reproduces guide:1485's documented cascade, replacing the whole clump at paint time, which is why the pass itself never needs to iterate.

There is deliberately NO pass after S5. Connection painting can carve new water and whether the engine dresses that is unmeasured; the one datum pointing at it points the other way, since `beach_terrain` is documented to stop working entirely when a `<CONNECTION_GENERATION>` section exists. Measured cost of leaving it out, at seed 7 on Normal: 873 unbeached coastal tiles on Pag and 829 on `24hr_Mont Saint Michel.rms`, against 0 on `AK_Namatjira.rms`.
- Failures: `terrainAbsent` (no eligible tiles at all — e.g. base_terrain never present on the map: a real, common map bug this preview should surface), `spacingConflict` (eligible set emptied by spacing), `growthShortfall` (partial growth — the same bucket S1 and S2 use; rev 3 invented a `budgetShortfall` name here that was never in Sec.7's union, so Sec.13's per-bucket unit test could never have been written for it).

### 6.5 Connections (S5)

Per connection command, build the node set: `create_connect_all_players_land` → player-land origins (incl. assigned lands); `…teams_lands` → **all pairs within each canonical team** (Sec.3.1), teams taken independently, no cross-team pairs. **Un-teamed players produce no pairs at all — including with each other.** Canonical team 0 is "not on a team", not "the team of everyone left over", and an implementer who treats it as a group draws land bridges between players who are not allies, which is exactly the kind of confident lie goal 1 forbids. A lobby with no teams therefore yields no team connections, and the Sec.3.1 `"teams"` drawer note fires; `…all_lands` → all land origins, all pairs, regardless of zone. `…same_land_zones` → **GROUPS by `.zone` and connects all pairs WITHIN each zone independently, never across zones — CORRECTED 2026-08-06.** A prior reading of this section parsed "`…all_lands` / `…same_land_zones` → all land origins, all pairs" as one shared behaviour for both commands, which an implementation session built and shipped before review caught it. That was wrong: cross-checked against two independent community RMS references (not the guide this section otherwise cites, and not yet confirmed in-game the way this doc's RMSTEST_* runs confirm other facts — a real run is still owed here, tracked as a new Sec.15 verify item), both describing `same_land_zones` as zone-partitioned. It also fits the zone defaults Sec.6.1 already measured without needing a new assumption: every `create_land` shares zone −10 while every player land gets its own `playerNumber − 10`, so on an unmodified script this command connects only the neutral lands to each other and leaves player lands untouched — which is the entire reason it exists as something other than a plain synonym for `…all_lands`. `…land_zones z1 z2` → lands of those zones, all cross+intra pairs; `…to_nonplayer_land` → player×neutral pairs only (and emulate its documented bug: it blocks all subsequent connection commands — note emitted).

- Pathfinding: **one multi-source Dijkstra per SOURCE land**, not one search per pair — every tile of the source land starts at cost 0, and each of that source's targets is answered at whichever of its tiles the search closes first. Cost per tile = accumulated `terrain_cost` for its terrain (default 1; ≤0 → impassable). A heuristic is deliberately absent: A*'s optimality covers only the first goal popped out of a goal set, so aiming one at the nearest remaining target returns non-optimal paths to the rest. **Answer the unreachable pairs before searching**, by flooding the command's passable tiles into connected components once and asking whether the two lands share one — otherwise a single unreachable target makes its search exhaust the whole component and cancels the saving (measured 2026-08-11: batching alone bought `24hr_Caverns.rms` 15%, batching plus the component check 5.0×). A land is not symmetric here: it can DEPART from any component its tiles touch, since source tiles are seeded whatever their own terrain costs, but it can only be ARRIVED AT through its own passable tiles.
- Costs and replacements read the terrain state **at the start of S5** unless `accumulate_connections` (DE semantics — guide); with it, they read the state at the start of the CURRENT COMMAND. **Accumulation is between commands and not within one — measured, `RMSTEST_43a`/`43b`, Sec.15 item 22** (456 road tiles across eight generations, flag on and flag off, zero spread, against a control quantity that varied normally). Rev 6 and earlier said "prior connections' output" without saying at what granularity, and the implementation read it as live pair-to-pair; that reading is withdrawn. It also has to be, for the batching above: a per-command snapshot is what makes one search per source land equivalent to one per pair rather than a deviation.
- One further consequence of the frozen read, and it is the difference between a 3.0 s map and a 0.9 s one: within a command, **a tile's painted value is a pure function of the snapshot**, so a second disc covering it writes what is already there. Track which tiles a command has painted and skip the repeats. `24hr_Caverns.rms` declares `terrain_size DLC_RAINFOREST 420 0` on a 240-wide map — a disc larger than the map, re-scanned per path tile over thousands of them.
- No path (impassable moat of cost-0 terrain, or unreachable land) → that pair's connection simply isn't produced (engine behavior) + `connectionBlocked` failure with the pair identified — prime 5.2 material.
- Terrain application along the path: for each path tile, radius = `terrain_size[terrain].radius ± uniform(variance)` (per-tile roll; negative effective radius → replace nothing — guide:1965). **When no `terrain_size` entry exists for the terrain the path is crossing, radius defaults to 1 and variance to 0** (guide:1958/1960) — rev 3 left this unspecified, and it decides whether a default connection is drawn 1 tile or 3 tiles wide, which is about as visible as preview differences get; 2 of the 12 connection-using corpus maps omit `terrain_size` entirely. Note also that **radius 0 still replaces a single-tile-wide path** (guide:1963) — 0 is a real width, not a no-op, so the disc for radius 0 is the path tile itself. Within the disc, apply `replace_terrain old→new` (accumulated list; `default_terrain_replacement` = replace-everything, overriding earlier list entries but not later ones — emulate by expansion order). Replacements reference pre-S5 terrain per the same accumulate rule — so within one command they never cascade (`GRASS→DIRT` and `DIRT→WATER` in the same block leaves a grass tile at DIRT), and the radius lookup for a path tile reads the terrain the command STARTED with, not what an earlier disc has since painted onto it.

### 6.6 Objects (S6)

Sequential per `create_object` (order matters — engine places in order, first come first served). Object identity resolves through refDb; `create_object_group` picks per-placement uniformly from the group — the declared `%` weights are **ignored** in-engine, not inverted (guide:2025: "The % currently doesn't work; all objects in the group are equally likely regardless of what number you specify"), so uniform *is* the engine's current behaviour rather than an approximation of it. The note still earns its place: it tells the author their percentages are inert. Each placement re-rolls independently, including under a reference frame (guide:2023/2024), which is why a group should not mix objects with different resource amounts.

**Counts:** `number_of_objects` (default 1) × `number_of_groups` (default: ungrouped); `group_variance v` varies each group's count within `[n−v, n+v−1]` (positive range reduced by 1 — guide), floored at 1; `set_scaling_to_map_size` ×`dim²/10000` (Sec.4), `set_scaling_to_player_number` ×playerCount — **mutually exclusive** (guide); if both appear, **last wins** — *sourced*, not extrapolated: guide:167 states the general rule ("if you duplicate an attribute or use mutually exclusive attributes, the final one will apply") and guide:1257/1274 repeat it for the scale-attribute pairs. Scaling applies to groups when grouping is present, else to objects (guide).

**"Grouped" is a derived flag, and four different attributes set it.** Everything downstream keys on this — the anchor-versus-member rule below, whether scaling multiplies groups or objects, whether `force_placement` is disabled — so compute it once per command and pass it down rather than re-deriving it per predicate:

```
grouped = number_of_groups present
       || group_placement_radius present     (guide:2100, "Activates grouping behavior")
       || set_tight_grouping present         (guide:2120, same wording)
       || set_loose_grouping present
```

`number_of_groups` is the one the rest of this section names, but it is not the only trigger: `create_object GOLD { number_of_objects 5 group_placement_radius 3 }` **is** grouped, with one group of five. Reading grouping off `number_of_groups` alone silently treats that command as five independent scatter placements, which is the wrong branch of every rule below.

**LOOSE is the default when grouping is active and neither mode is stated — MEASURED, `RMSTEST_46a/46b/46c`, one mode per file and three runs each (Sec.15 item 17c, BUG-011, applied 2026-08-12).** Off-patch fraction against a `terrain_to_place_on` patch: tight **22–35%**, explicit loose **0%**, unstated **0%**. An unstated command is checked per member, so **tight is opt-in**.

The opposite was inferred, correctly flagged `[verify]`, and shipped for the whole of Phase 4: the guide never states a default, and `group_placement_radius`'s own description ("the number of tiles out from the central tile that objects belonging to the same group may spawn") reads as a cohesive cluster with `set_loose_grouping` as the opt-in. **It governs 498 of the corpus's 964 grouped `create_object` commands** (380 declare tight, 86 loose), which is why it was worth a run: the flip changes which branch of every constraint in this section runs for more than half of all grouped placements. **Corpus effect, measured at seed 7 on Normal: 13 of 32 maps change, all downward, 159,732 → 141,281 placements.** Fewer objects, in legal positions instead of illegal ones — `OWWC1Tewaipounamu` 11,068 → 2,336 and `24hr_Mont Saint Michel` 9,899 → 1,946 are the two large ones, both maps whose grouped commands were previously filling through terrain they cannot occupy.

**Recorded and deliberately not tuned to:** explicit loose placed exactly 24 objects in all three runs where unstated placed 32, 32 and 40. Zero spill in both makes them identical on the rule this is about, but a consistent count difference says they are not the same code path. Separating a cap from a rejection rate needs its own run.

Rev 6 argued the point from "26 of 32 corpus maps state `set_loose_grouping` explicitly, so this default governs the remainder rather than nothing", and that reasoning does not hold: the count was per *file* where the rule is per *command*, the figure was 25 not 26, and the maps not stating loose overwhelmingly state **tight** rather than nothing (30 of 32 use `set_tight_grouping` somewhere). At file granularity the answer is that **zero** maps leave it undeclared, which would have retired the question entirely — and is wrong. A per-file count of a per-command property can be wrong in either direction; here it was wrong in both. (Method: comment-stripped scan of `create_object … { … }` bodies, grouping detected by the four triggers above.) It is a one-map test on the same instrument as Sec.15's others — a group with `group_placement_radius` and no mode, against a constraint that discriminates anchor-checking from member-checking.

**Ownership — `set_gaia_object_only`, and the gate it puts in front of every per-player resource.** 31 of the 32 corpus files use this attribute. Reference-frame logic that ignores it cheerfully places per-player gold, boar and berries that the engine places nowhere, so it gates everything below.

Guide:2354: "Use with `set_place_for_every_player` to place gaia (neutral) objects on a per-player basis. **Must** be used when placing player's gold/stone/berries/deer/boar." Guide:2262 states the same constraint from the other side, under `set_place_for_every_player`: objects that cannot be owned by players "also require `set_gaia_object_only` to be placed for every player."

So the rule, pinned: **a `create_object` with a reference frame (`set_place_for_every_player` or `place_on_specific_land_id`) naming an object that cannot be player-owned, and lacking `set_gaia_object_only`, places nothing.** Zero placements, one `gaiaOnlyRequired` failure (Sec.7) carrying the command span, and a note. **CONFIRMED in-game** (Test 3, 2026-07-30): two identical per-player commands in separate distance bands, one with the attribute and one without — the gold ring appeared, the stone ring did not appear anywhere on the map. Not placed-and-owned, not placed-as-gaia: nothing. Sec.15 item 9 is answered and closed. This is not us being strict — it is the engine's behaviour, and it is one of the most common beginner mistakes in RMS, so surfacing it is worth more than any layout detail on the page. It is also a clean `validate()` hook (a static check needing no generation at all) and should be raised there when `validate()` ships; the preview flagging it is the cheap interim.

"Cannot be player-owned" needs data: **`playerOwnable: boolean` per object, Sec.12 item 3.** Fallback until it exists: treat objects whose `category` is a gaia resource (gold, stone, wood/forage, huntable) as requiring the attribute, treat everything else as ownable, and emit the note at reduced confidence ("this object may need `set_gaia_object_only`"). Sheep and other herdables are the awkward case the flag exists to settle — guide:2355 notes gaia-only "can be used for controllable objects (for example, sheep)", i.e. it is permitted but not required for them, so a fallback that guesses from category alone will mis-handle herdables in one direction or the other. Get the flag.

`set_gaia_unconvertible` and `set_gaia_civilization` affect ownership and appearance, never position — accepted silently under Sec.9 item 5.

**Reference frame — it anchors distances, it does NOT confine the candidate set (rev 6, measured).** This is the single most load-bearing correction in this section, because the natural reading of "place for every player" is "place *on* that player's land", and that is not what the engine does. A frame supplies the origin that `min`/`max_distance_to_players`, `find_closest` and friends measure *from*. It does not restrict candidate tiles to that land. Verified twice: in Test 7 and Test 9 a `place_on_specific_land_id 5` object appeared in clearings belonging to no such land, and in Test 1 a `set_place_for_every_player` object placed several of one player's allocation inside another player's clearing. What actually confines placement is the terrain-separation rule below, plus whatever distance band the command declares — so **a frame with no distance band confines nothing**, and a map relying on the frame alone scatters. `avoid_other_land_zones` is the attribute that genuinely restricts to the referenced land.

- `set_place_for_every_player`: iterate player lands (per land, not per player — multiple create_player_lands → multiple placements unless `generate_for_first_land_only`); all constraints evaluated relative to that land's origin. **A land carrying `land_id` is skipped** — guide:2263 ("Only works for player lands or lands assigned to players. **Disabled by land_id**") and guide:1146, which explains why anyone would do that: it is the "fake player lands" idiom for generating forests or ponds between players. Placing objects on those lands anyway would be a confident lie in exactly the shape goal 1 forbids, so: no placement, one `landMissing` failure per intended placement, and a note naming the land.
- `place_on_specific_land_id id`: iterate lands with that id (−11 → random map position). Missing id → `landMissing` failure for every intended placement.
- Neither → gaia scatter anywhere valid; `max_distance_to_players` inert (guide says only *maximum* "has no effect" without a frame). **`min_distance_to_players` still applies frameless — pinned:** candidate must be ≥min from *every* player-land origin (Chebyshev, or Euclidean under `set_circular_placement`) — this is how real maps keep neutral resources off starting towns. Also inert without a frame (all guide-marked "Requires: set_place_for_every_player or place_on_specific_land_id"): `find_closest`, `find_closest_to_map_center`, `find_closest_to_map_edge`, `ignore_terrain_restrictions`, `require_path`, `avoid_other_land_zones`, `generate_for_first_land_only` — accepted with a SimulationNote, not an error.

**Candidate filter** (each check is a named predicate contributing to Sec.7 failure attribution):

- `occupied` free (unless `force_placement` — stacking allowed, occupancy skipped; force_placement is disabled under `set_loose_grouping` — guide:2739);
- **can-overlap: multi-tile objects are silently dropped by two constructs, and Sec.9's one-tile model hides it.** guide:2121, under `set_tight_grouping`: "Objects that are larger than one tile and cannot overlap (most buildings), will **not be placed**" — not placed badly, not placed at all. guide:2738 says the same from the other side: `force_placement` "only works for objects that can overlap on the same tile (ie. units, but not buildings)". Sec.9 item 11 defers footprints to v1.x and treats every object as one tile, which is fine for *where* things sit and wrong for *whether* they exist: a tight-grouped row of houses renders as a tidy cluster the engine places nowhere. Same shape as the `set_gaia_object_only` gap, and equally cheap to close without a footprint model — one `canOverlap` bit per object, derivable from Sec.12 item 8's `category` (buildings vs everything else) at reduced confidence, or better as a companion flag to item 3's `playerOwnable`. Rule: under `set_tight_grouping`, a non-overlapping object places **nothing** plus a `notSimulated` note naming the reason; under `force_placement`, a non-overlapping object degrades to ordinary occupancy-respecting placement plus a note;
- terrain habitat: object's coarse habitat class from refDb (`land`/`water`/`amphibious`/`shore`/`any` — Sec.12 item 7; default `land` for anything undeclared) matches the tile. `water` is open water only; `amphibious` adds the shallows and the beaches; `shore` is open water touching a beach. **Four composition rules, three corrected 2026-08-07 after all three shipped backwards and the fourth on 2026-08-08:**
  - `terrain_to_place_on` and `layer_to_place_on` narrow EACH OTHER (guide:2483: "only where both the base terrain and the layer apply"), rather than either standing alone.
  - the habitat check is **additional** to `layer_to_place_on`, not replaced by it — a layer is a visual property and says nothing about the ground the object stands on.
  - **and it is additional to `terrain_to_place_on` too, whenever the habitat is DATA rather than the `land` fallback — corrected 2026-08-08.** `terrain_to_place_on` was previously treated as an outright exception, on the reading that it "names the ground itself, so an explicit statement outranks a guessed habitat class". The premise is right and the conclusion does not follow: **naming a terrain does not lift the engine's terrain table**, and the proof is the placeholder idiom read from the other side. If `terrain_to_place_on SHALLOW` were enough to put a fish on a shallow, `Menindee_AUS_v2.3.rms` would write `create_object FISH { terrain_to_place_on SHALLOW }`; it instead pays for `create_object FISH_PLACEHOLDER { terrain_to_place_on SHALLOW … second_object FISH }`, where the placeholder is unit 647 carrying terrain restriction 0. Nobody buys an unrestricted carrier if naming the terrain already works. guide:2510 names the real override and it is `ignore_terrain_restrictions`. Left uncorrected, `AK_Hourglass_v2.0.rms`'s `create_object SHORE_FISH { terrain_to_place_on WATER number_of_objects 200000 }` had no shore constraint at all — 788 shore fish over open sea, 245 once both apply. **The carve-out survives for exactly the case that motivated it and no wider**: an UNDECLARED habitat is a guess, the data covers a few dozen objects of several hundred, and narrowing an unknown water object by a guessed `land` would place nothing and read as failure rather than as a restriction. Measured across the tracked corpus: four maps change, every difference is SHORE_FISH, and `Menindee`'s object count is identical.
  - `ignore_terrain_restrictions` bypasses **the habitat check only**, never the script's own `terrain_to_place_on`/`layer_to_place_on`. guide:2510-2511 both defines it as lifting the terrain the object is "normally restricted from" and states it "can be used in combination with `terrain_to_place_on`". **Frameless, the flag is INERT — MEASURED 2026-08-11, `RMSTEST_42`, four runs.** Its own documented requirement ("must be used with `set_place_for_every_player` or `place_on_specific_land_id`") neither voids the command nor is ignored: the command places its full count and the object keeps its own terrain restriction. Sixty salmon from a flagged command plus an unflagged control, **all sixty in water**, and thirty flagged olive trees on grass. So a frameless `ignore_terrain_restrictions` is an attribute that does nothing, and the `create_object` around it is untouched.

    **Three readings were live and the document contained two of them while the code implemented the third.** Sec.6.6's frame list above (`max_distance_to_players` inert, `find_closest` inert, this flag inert, "accepted with a SimulationNote, not an error") was right all along. This sentence said the opposite — that the bypass applies anyway — and `objects.ts` plus RMS0315 shipped a third reading on 2026-08-10 in which the unmet requirement empties the whole command, on the strength of `AK_Namatjira.rms` placing zero shore fish. Namatjira could never separate the three: its command also names a shallow, and a shore-habitat fish on a shallow places nothing under the inert reading too. **A map that produces zero is consistent with every model that produces zero**, which is why it took a script whose flagged and unflagged arms differ in nothing else.

    The corpus argument had been written down and was not weighed: `find_closest` carries the identical `Requires:` line and appears 71 times frameless in working maps, so the line plainly does not void commands. It sat in `RMSTEST_42`'s own header, written before the run, as the reason to expect this result.

    **Consequence, tracked as BUG-007:** revert the whole-command gate in `objects.ts` to flag-is-inert, re-scope RMS0315 from "this command places nothing" to "this attribute does nothing here", and strike the 47-command corpus figure rather than leaving it to age.
- **implicit terrain-separation (default-ON for every frame-referenced placement) — CONFIRMED in-game, with one sharp clarification:** the candidate must be *reachable from the reference land's origin* through tiles the object is not habitat-restricted on. The guide states this for both `set_place_for_every_player` and `place_on_specific_land_id` ("only be placed where they are not separated from the origin of their land by a terrain they are restricted on"). This — not the opt-in `require_path`, and not the reference frame itself (see above) — is the *only* thing that keeps island resources on the owning player's island.

  **The clarification, and it is the whole rule: separation is decided by TERRAIN RESTRICTION, never by occupancy or by what merely looks like a barrier.** Verified by running the same script twice with only the base terrain changed (Test 1, 2026-07-30): with **WATER** between the clearings each player's stone stayed on its own land, because gold and stone are terrain-restricted from water. With **FOREST** between the clearings the same stone scattered freely across every clearing, because forest is a perfectly legal terrain for stone — the trees block by *occupancy*, and occupancy is not separation. A dense forest wall that no unit could ever cross does not separate anything, and modelling it as a barrier would confine resources the engine happily scatters.

  Consequence for the habitat model: the coarse `land`/`water`/`shore`/`any` classes of Sec.12 item 7 are exactly the right granularity — forest is `land`, so a `land` object is unrestricted on it and correctly passes through. Road terrains likewise do not count as separation (guide, and Sec.12 item 6's `isRoad` flag gates it). Bypassed by `ignore_terrain_restrictions`. Implement as one BFS reachability mask per (reference land, habitat class), cached for the stage;
- distance band `min/max_distance_to_players` from the reference origin — **square** (Chebyshev) by default, Euclidean with `set_circular_placement` (guide); `min > max` → deterministic zero placement, `minExceedsMax`;
- `avoid_other_land_zones d`: tile must belong to the referenced land, d from its edge;
- forest zone: `place_on_forest_zone` requires membership; `avoid_forest_zone d` requires distance ≥d (bare attribute → d=1 — guide);
- `avoid_cliff_zone d` (bare → d=1), `min_distance_to_map_edge d`, `max_distance_to_other_zones d` — **minimum, not maximum**, distance from terrain the object is restricted from (guide:2527, which says so in capitals), e.g. gold off coastlines. **This spec text was right and the code was not, from S6's first draft until 2026-08-08**: the predicate shipped as `dist <= d`, a maximum, so `QS_Three_Bays_v1.1.rms`'s "tuna everywhere" command (`max_distance_to_other_zones 4`) was confined to a 4-tile ribbon along the shoreline rather than pushed 4 tiles off it. Both halves were inverted — a tile with NO restricted terrain anywhere in reach cannot violate a minimum-distance rule, so `UNREACHABLE` must PASS, and the old code failed it, which placed zero objects on an all-water map. The correct shape is `dist === UNREACHABLE || dist >= d`, which is what the two sibling predicates in the same block already used. Nothing tested this attribute in either direction, which is how it survived sitting between two correct neighbours; it now has three tests, and **an attribute whose name contradicts its behaviour is the first one to write a test for**. Two carve-outs from the same entry: it **does not apply to road terrains** even though resources cannot be placed on them (guide:2530 — so the `isRoad` flag of Sec.12 item 6 gates this check as well as the separation rule), and it is inert for objects with no terrain restrictions at all (guide:2531), which under the `habitat: "any"` fallback is every unresolved object — worth a `[tune]` comment rather than a note, since the fallback is already noted once;
- **grouping scope — two rules, and they are measured, not inferred (rev 6).** Rev 4 replaced rev 3's blanket tight/loose policy with an eight-row per-attribute table, rev 5 kept it, and **in-game testing showed both revisions were wrong about the mechanism**. The rule is:

  > **Tight grouping: the ANCHOR is checked against every constraint, and the fill is checked against nothing.**
  > **Loose grouping: every member is checked against every constraint.**

  There is no per-attribute variation. The guide's tight/loose notes (guide:2122, 2143) describe this correctly at a coarse level; the per-attribute entries (guide:2431, 2529, 2569, 2584, 2598, 2614, 2635) describe *loose* behaviour and say nothing reliable about tight, which is why a table built from them inverted the answer for the corpus's most-used attributes.

  **What "anchor" means.** Not the geometric centre. The engine places one member, which must satisfy the constraints, then flood-fills the remaining members outward from it in an arbitrary direction without re-checking. So a tight group is an irregular blob whose *anchor* is legal and whose other members may sit anywhere — including squarely inside a zone the command asked to avoid. Modelling it as "constraints apply to the group centre" is close enough for placement statistics but wrong about shape, and wrong about which member is guaranteed legal.

  **Evidence (Phase 4.1 verification pass, `RMSTEST_*.rms`, 2026-07-30).** Three constraints of three different *kinds*, all behaving identically under tight grouping:

  | Constraint | Kind | Test | Result |
  |---|---|---|---|
  | `avoid_forest_zone 6` | distance avoidance | 1 | 5×5 gold block placed with members against the tree line; succeeded only on the seeds where the *anchor* had room |
  | `terrain_to_place_on DIRT` | tile validity | 8 | **25 of 25** placed on a ~9-tile dirt patch, spilling freely onto grass |
  | `avoid_actor_area` | area exclusion | 9 | gold anchored outside a terrain-marked actor area, then grew straight into it |
  | `min_distance_group_placement 12` | inter-placement spacing | 18 | six tight groups of 49; blob edges came within **8** tiles of each other |

  Test 8 is the decisive one for tile properties: the fill does not even check whether the tile is a *legal terrain* for the object. Nothing short of tile occupancy stops it. Test 18 extends the rule to a constraint of a different *shape* — one about distance from other placements rather than about the tile — which was the last plausible candidate for an exception. It agrees with guide:2614's "distance refers to the center of the group, not the individual members".

  And for loose grouping, Test 6: 12 requested, **exactly 9 placed**, in a 3×3 knot — 9 being precisely the number of tiles satisfying `avoid_forest_zone 6` in that clearing. Every member checked, and the shortfall is real (report `groupPartial`).

  **Consequences for the generator.** Tight: evaluate the full predicate set for the anchor only, then flood-fill neighbours subject to occupancy alone. Loose: evaluate the full predicate set per member, and report `groupPartial` with placed/requested when the valid set runs out. Do **not** implement a per-attribute scope table; do not model tight groups as centre-constrained.

  **Two things this reinterprets.** Guide:2102's "a perfect square worth of objects will be filled" cap is about *available* tiles, not constraint-valid ones — which is why Test 8 placed all 25. And Sec.9 item 15's honesty note gains a sibling: a tight group's non-anchor members are placed by the engine in violation of the command's own constraints, so a preview that enforces them per member is *more* correct-looking than the game and therefore wrong.
- actor areas: `actor_area_to_place_in` membership, `avoid_actor_area`/`avoid_all_actor_areas` exclusion (`avoid_actor_area` accumulates — Sec.3.10's outstanding data gap). `create_actor_area X Y Id Radius` records areas up-front regardless of script position (guide:1991; collected in S0 per Sec.3.12). **An id names a set of areas, not one area** — guide:1995: "multiple actor areas can share the same identifier", and `actor_area` on placed objects appends to that set as objects land. So both operations are over the union: `avoid_actor_area 1234` must clear *every* area carrying id 1234, and `actor_area_to_place_in 1234` admits a tile inside *any* of them. Store areas as a multimap keyed by id; a single-area-per-id model silently ignores all but one on maps that reuse ids, which the guide's own idiom encourages. **Its X/Y are absolute tile coordinates, NOT percentages** (guide:1994 states this in capitals — "the X and Y coordinates are in tiles, NOT % of map width"), and Radius is a **square** radius. Do not route these through Sec.4's `land_position` percent→tile conversion; they are already tiles, and the guide's own example scales them by hand per map size. `actor_area`+`actor_area_radius` on placed objects append areas as they place; `actor_area_radius` defaults to **1** (a 3×3 area — guide:2780), and objects sharing an id all inherit the radius of the first one successfully created. Referencing a never-created id → `actorAreaMissing`;
- `min_distance_group_placement` (persistent spacing vs all prior and future placements) and `temp_min_distance_group_placement` (this command only) via a spacing field on placements;
- `require_path dev`: BFS from candidate to land origin over passable (non-habitat-blocking, non-cliff, non-wall) tiles; dev 0 = any path, 1 = path length ≤ **1.3× [tune]** straight-line, larger dev looser. Applies only to a group's first member (guide). **Note the degradation:** Sec.9 item 4 excludes walls from simulation, so no wall tiles exist in the grid and the "non-wall" clause is inert — on a walled map `require_path` will report paths the engine would reject. One note, emitted alongside the existing per-wall-object note, when a script combines walls with `require_path`.

**Selection:** uniform random from surviving candidates — we always shuffle, so `enable_tile_shuffling` is accepted as a no-op. **The honesty cost sits on the attribute's *absence*, not its presence** — which is the opposite of the intuitive reading, so note it carefully. Guide:2694: without it the engine increases randomness "rather than just using the first entry" of the candidate list — so a script that omits the attribute gets *deterministic* placement from the engine and *shuffled* placement from us. Guide:2697 makes that a real difference rather than a nicety: the attribute "should NOT be used when attempting to place objects in a specific precise location (i.e. placing herdables or villagers under the town center)", which is precisely the idiom our always-shuffle scatters. One note when a frame-referenced `create_object` omits `enable_tile_shuffling`, deduped per command; listed in Sec.9 item 15 alongside the west bias, since it is the same class of erased engine determinism. Except `find_closest` (min distance to land origin), `find_closest_to_map_center`, `find_closest_to_map_edge` (override precedence per guide). **`find_closest` measures Euclidean distance while every other distance constraint here is square/Chebyshev by default** — guide:2652 calls this out in capitals as a common surprise, and notes the consequence (`find_closest` + `min_distance_to_players` tends to place objects at 90° to each other, because the square's corners are further from the center than its edges). This doc mixes both metrics deliberately; implement each as written rather than unifying them. Groups: tight → flood-fill adjacent tiles from the group center; when tiles run out, place what fits (guide: "a perfect square worth of objects will be filled" — a capped partial fill, NOT all-or-nothing) and report `groupPartial` with placed/requested; `occupancyFull` is reserved for the zero-tiles case. Loose → independent placements within `group_placement_radius` (default 3), individual misses allowed (partial → `groupPartial` — mirrors the engine's documented behavior).

**Output:** `PlacedObject { objectRef, x, y, player?, category, groupId? }`. Player markers: one `PlayerMarker { player, x, y }` per player-land origin (renderer draws numbered flags). VILLAGER/SCOUT count quirks are cosmetic — place the declared count, note that DE spawn-count special-casing is not simulated. Walls: **not simulated** (Sec.9) — one note per wall-type create_object.

## 7. Placement instrumentation — the 5.2 contract

The non-negotiable rule: **no placement primitive returns a bare boolean.** The shared vocabulary:

```ts
type PlacementOutcome<T> = { ok: true; value: T } | { ok: false; failure: PlacementFailure };

interface PlacementFailure {
  bucket: FailureBucket;
  commandSpan: Span;          // originating command's source span (click-through)
  stage: StageId;
  entity: string;             // "GOLD", "land #3", "connection P2–P5", …
  reference?: string;         // player/land frame if any
  detail: string;             // human sentence, beginner-first, like parser diagnostics
  data?: Record<string, number | string>;  // bucket-specific (e.g. owned/target)
}

type FailureBucket =
  | "noValidTiles"          // constraint intersection empty (generic terminal)
  | "terrainAbsent"         // required terrain/layer never present on the map
  | "spacingConflict"       // a spacing/avoidance constraint emptied the set
  | "occupancyFull"         // tiles exist but are taken (tight group / crowding)
  | "minExceedsMax"         // deterministic: min_distance > max_distance
  | "landMissing"           // place_on_specific_land_id unmatched / player land absent / land_id land skipped
  | "actorAreaMissing"      // referenced actor area never created
  | "pathBlocked"           // require_path found no acceptable path
  | "connectionBlocked"     // no route between a connection pair
  | "originFallbackCenter"  // land origin placement exhausted → engine center fallback
  | "growthShortfall"       // land/terrain/elevation grew < target (data: owned, target, blocker)
  | "groupPartial"          // loose group placed k of n members (data: placed, requested)
  | "zoneAvoidanceBlocked"  // other_zone_avoidance rejected a single placement
  | "borderBlocked"         // border constraint rejected a single placement
  | "playerOriginAvoidance" // elevation/terrain seed set emptied by player-origin avoidance (Sec.6.2/6.4)
  | "gaiaOnlyRequired"      // frame-referenced create_object of a non-ownable object without set_gaia_object_only (Sec.6.6)
  | "iterationCapped"       // Sec.11 per-command iteration cap hit — truncated, not blocked
  | "notSimulated";         // feature in Sec.9's list — placement skipped, honesty bucket
```

**Union completeness is a merge gate, not a formality.** Sec.13 requires one unit test per bucket, so a bucket a stage emits but the union omits is a test that can never be written. Rev 3 emitted `playerOriginAvoidance` (Sec.6.2) and `budgetShortfall` (Sec.6.4, Sec.11) from stages that had no matching union member; the first is now a member, the second is gone — Sec.6.4 uses `growthShortfall` (same concept, one bucket) and Sec.11's cap uses `iterationCapped`.

**Bucket domains are disjoint (pinned).** `growthShortfall` is the *region* bucket: any land/terrain/elevation that finishes below target, with `data.blocker ∈ {border, zone, space}` naming the dominant cause. `borderBlocked` and `zoneAvoidanceBlocked` are *single-placement* buckets: an object or origin rejected by that one constraint. They never compete, because they describe different kinds of event — rev 3 let them overlap on the land-growth path with no precedence rule, which is precisely where the stable bucket identity this section optimizes for would have gone unstable.

**Every bucket names its emitter, and this is the other half of the merge gate.** Sec.13 requires one unit test per bucket, so a bucket the union declares but no stage emits is a test that *cannot be written* — the same defect as a bucket a stage emits but the union omits, which is the only direction rev 3 through rev 6 checked. Three were in that state and are pinned here:

| bucket | emitter |
|---|---|
| `borderBlocked` | **S6**, `min_distance_to_map_edge` rejecting a candidate (Sec.6.6's candidate filter). *Not* S1 growth — a growth candidate rejected at a border contributes to that land's `growthShortfall` with `blocker: border`, and reporting each rejected growth candidate separately would put tens of thousands of records into a report 5.2 aggregates by count. |
| `zoneAvoidanceBlocked` | **S6**, `avoid_other_land_zones` rejecting a candidate. Same split: S1's `other_zone_avoidance_distance` rejections roll up into `growthShortfall` with `blocker: zone`. |
| `pathBlocked` | **S6**, `require_path` finding no acceptable path for a candidate (Sec.6.6). Distinct from `connectionBlocked`, which is S5's pair-level bucket. |

The general rule the three cases share: **region stages roll their per-candidate rejections into one terminal `growthShortfall` carrying the dominant blocker; the objects stage reports per placement.** That is what makes the two families disjoint, and it is why the constraint names appear in both places without ambiguity.

**Attribution (one algorithm, pinned).** Evaluate predicates as **successive set intersections in a fixed, documented order** — and attribute the failure to the predicate whose intersection first produced the empty set; if the set was empty before any predicate ran, `noValidTiles`.

**The order is per stage, and every stage has one.** Rev 5 pinned only S6's (Sec.6.6's candidate-filter list, top to bottom), which left four stages that emit buckets with no documented order — and since 5.2 aggregates on bucket identity and Sec.13 requires a test per bucket, an undocumented order there is the same defect one stage over. **The rule: each stage's attribution order is its own constraint list, in the order written in its subsection.** Concretely — S1 lands: border, then zone avoidance, then already-owned (Sec.6.1's rejection list). S2 elevation: terrain match, then player-origin avoidance (Sec.6.2's seed criteria). S4 terrains: eligible-terrain match, then height limits, then `spacing_to_other_terrain_types`, then each `spacing_to_specific_terrain`, then flat-only, then `set_avoid_player_start_areas` (Sec.6.4's list). S6 objects: Sec.6.6's candidate-filter list. When editing those subsections, treat their bullet order as normative rather than editorial. This is deterministic (the order is fixed and written down), it costs one pass, and it produces the same bucket for the same script every time, which is what 5.2 aggregates on. Rev 3 stated a *different* algorithm as normative — leave-one-out, "the first single predicate whose removal leaves a non-empty set" — and then described successive intersection as a cheap implementation of it. They are not the same algorithm and disagree whenever two predicates overlap; leave-one-out also costs N passes. Leave-one-out is withdrawn. Buckets are deliberately coarse — 5.2's report UI aggregates by bucket, and stable bucket identity matters more than forensic precision.

**Failures are COALESCED by bucket per command, as they are made** (2026-08-07). The first failure of a bucket is kept whole and stands as the example; every later one of the same bucket increments its `occurrences`. This follows directly from the sentence above — nothing downstream ever reads the second record of a bucket — but it has to be stated, because the uncoalesced version is not merely untidy. Measured over the tracked corpus: `Menindee_AUS_v2.3.rms` produced **280,427** failure records in one generation, `TC2 - Comeer v1.4.rms` 185,432, `24hr_Caverns.rms` 172,650, each an object carrying a freshly built sentence. They are allocated during generation, structured-cloned across the worker boundary on every keystroke burst, and rendered as one list item each the moment the notes drawer opens. Coalescing takes that map from 280,427 records to 165. **Consumers must sum `occurrences` rather than count records** when they report a total, or a quarter of a million failed placements reads as six.

`PreviewResult.reports: CommandReport[]` — one per instantiated generative command: `{ commandSpan, stage, attempted, placed, failures: PlacementFailure[] }`. In batch mode (5.2) this is the entire output; in preview mode the pane surfaces a compact count ("3 placements failed — see notes") linking to spans.

**Reports are unconditional — there is no `collectReports` option.** Rev 5 carried one annotated "true always in practice", which is an unspecified state waiting to be guessed at: the field is non-optional on `PreviewResult` and nothing said what it held when the flag was false. Reports are also cheap (one record per command, not per tile) and they are goal 2, so no caller wants them off. `collectSnapshots` is the only cost knob (Sec.10). If batch allocation ever bites, the thing to cut is the per-failure `detail` sentence — a Sec.11 profiling decision, not an API surface.

## 8. Seeded RNG and re-roll

- PRNG: **mulberry32** (or splitmix32) — tiny, fast, deterministic across JS engines; quality is ample for a visual heuristic. No `Math.random()` anywhere in `src/preview/generator/`.
- **No `Math.sin`, `Math.cos`, `Math.pow`, `Math.sqrt`, `Math.hypot`, `**`, or `Math.log` either — same reason.** ECMAScript leaves these implementation-defined to the last bits, so a V8 upgrade (never mind a different engine) can change a result, and goal 5's byte-for-byte claim would be false everywhere they appear.
- **The lint rule is normative and it lands with `rng.ts`, not "in 4.3".** Rev 6 wrote "lint-enforced if practical" and Sec.14 wrote "CI-greppable", and neither existed: `eslint.config.js` carries no `no-restricted-properties`, `no-restricted-globals`, `no-restricted-syntax` or `no-restricted-imports`, and `.github/workflows/ci.yml` runs lint → typecheck → test → validate:reference with no grep step. So the load-bearing guarantee in this document — the one that makes the re-roll button meaningful and 5.2's Monte Carlo reproducible — was resting on a rule nobody had written. "If practical" is also the weakest phrasing in a spec that quantifies everything else. Concretely, in `eslint.config.js`, as a block scoped to `files: ["src/preview/generator/**/*.ts"]`:
  - `no-restricted-properties` on `Math`: `random`, `sin`, `cos`, `tan`, `pow`, `sqrt`, `cbrt`, `hypot`, `log`, `log2`, `log10`, `exp`, `atan2` — each with a message pointing at this section. (`floor`, `round`, `abs`, `min`, `max`, `sign`, `trunc` are exact and stay allowed.)
  - `no-restricted-syntax` on `BinaryExpression[operator="**"]` and `AssignmentExpression[operator="**="]`, which `no-restricted-properties` cannot see.
  - `no-restricted-imports` on `react`, `react-dom`, `monaco-editor`, `@monaco-editor/*` and `@tauri-apps/*`, scoped to **all three** pure areas — `src/parser/**`, `src/breakdown/patch/**` and `src/preview/generator/**`. The first two are a CLAUDE.md hard rule that is *currently unenforced*, so this closes an older gap than the one it was written for. Note the deliberate exception in Sec.2: `src/generationSettings/generationSettingsConstants.ts` and `teamModel.ts` are importable and must not be caught.
  - **Mutation-test both halves before believing either** (CLAUDE.md: a check that has only ever passed proves nothing). Add `Math.sqrt(2)` to a generator file → `npm run lint` exits non-zero; add `import { useState } from "react"` to a parser file → non-zero; restore both. Sec.13 records this, because Sec.13 is what gates merges. There is no need for them: the player ring uses a **precomputed integer sine table** (3600 entries, fixed-point, checked into `rng.ts`'s neighbourhood as data), clumping weights are **integer buckets** (Sec.6.1), and every Euclidean comparison — `set_circular_placement` bands, `find_closest`, `require_path` straight-line ratios — is done on **squared distances with integer arithmetic** (compare `dx²+dy²` against `d²`, and `len² · 100` against `straight² · 169` for the 1.3× ratio). `Math.floor`/`round`/`abs`/`min`/`max` are exact and fine.
- **Substreams:** stream seed = `hash(masterSeed, stageId, commandOrdinal)` (e.g. splitmix of the tuple). Each instantiated command draws only from its own substream; stage-0 randomization (start_random rolls, rnd()) uses per-node substreams keyed by node ordinal. Consequence: editing one create_object does not reshuffle lands or unrelated commands — *best-effort* stability (shared state like occupancy still cascades), a deliberate UX choice the real engine does not share; documented in the help popup, harmless to honesty since our seeds never match DE's anyway.
- **UI:** seed chip (current seed, editable number field) + re-roll button (new random seed) in the preview pane header, both HelpTip-wrapped. Copyable seed so users can share "this preview arrangement". The help text explicitly says previews with the same seed match *each other*, never the in-game map — and mentions that DE shows its own map seed in the Objectives screen for eventual side-by-side checking (parser-design Sec.13.9).

`PlacedObject`, `PlayerMarker`, `CommandReport`, `PlacementOutcome`, `PlacementFailure`, `FailureBucket`, `TileGrid` are defined in Sec.4/6.6/7. Together with the five above, that is every type `types.ts` owns — 4.2 builds its hardcoded fixture against exactly this list, and rev 3 left `StageSnapshot`, `SimulationNote`, `StageId` and `Span` as undefined field types that 4.2 could not have constructed.

**Worker protocol.** It *does* mirror `src/editor/parserWorker.ts` after all, for the reasons below: one long-lived worker, an incrementing id, the worker importing its own reference data, and stale responses discarded by id on the host (`useParsedDocument.ts:95` — the worker itself just echoes `requestId` back). The only addition is a watchdog for pathological runs.

```ts
type PreviewRequest  = { id: number; parse: ParseResult; settings: PreviewSettings; opts: PreviewOptions };
type PreviewResponse = { id: number; ok: true; result: PreviewResult }
                     | { id: number; ok: false; abandoned: true };   // watchdog only, see below
```

Note the response is a **discriminated union** — rev 3's protocol promised a `{ id, cancelled: true }` message while typing the return as an unconditional `PreviewResult`, which has no representation for a run that produced nothing.

**`refDb` is not in the message.** The worker imports `language.json` and `game-constants.json` directly, exactly as `parserWorker.ts:7-8` does. Rev 4's signature took `refDb` as a parameter while its `PreviewRequest` had no field for it, leaving the implementer to invent one; shipping it per request would also structured-clone ~111 KB of JSON on every keystroke burst for data that never changes.

**Cancellation: there isn't any in v1, and that is the right call.** `generatePreview` is synchronous, so a dedicated worker's `onmessage` cannot fire mid-run, and a `checkCancelled` function cannot cross `postMessage` at all (structured clone throws `DataCloneError` on functions) — rev 3's option field was unsendable. Rev 4 replaced it with terminate-and-respawn and argued the cost was "paid rarely at a ~300 ms debounce", which is backwards: cancellation fires *only* when a new request arrives mid-flight, i.e. during continuous typing, so the respawn cost lands exactly in the regime it was supposed to be rare in — and it is unquantified in a document that quantifies everything else (worker boot, module init, re-parsing 111 KB of `language.json`, re-cloning the whole ParseResult).

So v1 does what the parser already does, and this time the claim is accurate: **the host keeps one long-lived worker and discards stale responses by id** (`useParsedDocument.ts:95` is the existing precedent — `if (source === undefined || requestId !== latestRequestIdRef.current) return;`). A superseded run finishes and its result is dropped. At the Sec.11 budget that wastes ≤40 ms of worker time and costs the UI nothing, which is strictly cheaper than a respawn.

**Watchdog, for the pathological tail only.** If a request is still outstanding after **12 s [tune]** the host calls `worker.terminate()` (which does kill a synchronous run), spawns a replacement, emits `{ ok: false, abandoned: true }` for the outstanding id, and re-posts the current request — **at most twice**, after which it stops and leaves the pane showing the last good result. That bounds the damage from a script that defeats the iteration caps without paying respawn costs on ordinary edits.

**Both numbers were wrong on 2026-08-06 and the failure mode is worth recording, because the reasoning that produced them looks sound.** This said "1000 ms [tune] — Sec.11's hard ceiling plus headroom", derived from the 40 ms target below. But **the budget is a target, not a measurement of the shipped pipeline**: timed over the 32 tracked maps on 2026-08-07, a full `generatePreview` runs a median of ~460 ms and up to 3.8 s, so roughly a third of the corpus exceeded the watchdog every single time. And because the retry re-armed the watchdog with no counter, those maps were killed, re-posted, and killed again forever — they never rendered at all and pinned a core until the user typed something else. **A watchdog set below the real cost is a denial of service on the feature it protects, and an unbounded retry turns a deterministic slowdown into an infinite loop.** Set the ceiling from a measured distribution with wide margin; every real generation must finish well inside it or the mechanism is fighting the thing it exists to guard. Revisit the 12 s only against a fresh measurement, never against the 40 ms target.

The generator still takes an internal stop hook — `runStages(…, shouldStop: () => boolean)` constructed *inside* the worker, never posted — so that a real cancellation mechanism drops in later without a rewrite. Under the discard-by-id model it is the constant `false`. The upgrade path if profiling ever demands it is a `SharedArrayBuffer` cancel flag the generator polls, which needs cross-origin isolation and is therefore a genuine decision about Tauri's protocol headers, not a detail to slip in during 4.3.

UI debounce: regenerate **~300 ms [tune]** after the parse settles (parser reparse is its own 150 ms debounce upstream). Snapshot grids come back as Transferables to avoid copies.

## 11. Performance budget

- Target: full pipeline (no snapshots) on a 200×200 Arabia-like script in **≤ 40 ms**; with snapshots ≤ 80 ms. Hard ceiling 500 ms at 480×480 on pathological scripts (9320-clump commands) — beyond that, per-command iteration caps kick in (growth rounds capped at `4·dim²` total steps per command **[tune]**; report the truncation as an `iterationCapped` failure plus a SimulationNote, never hang).
- 5.2 batch feasibility: 1000 runs at 120×120, reports-only → **~15 ms/run**, ~15 s total, in the worker, **cancellable between runs** — matching CREATION_PLAN 5.2's "seconds, not minutes".

**The two bullets above are one budget, and rev 6's were three times apart.** "Reports-only" *is* `collectSnapshots: false` — Sec.7 pins reports as unconditional and `collectSnapshots` as the only cost knob — so both bullets describe the same work at two sizes. Everything Sec.11 specifies is per-tile or per-candidate (typed-array passes, distance transforms, BFS masks, frontier draws), so area is the right first-order scaling, and `120²/200² = 0.36` puts the batch figure at **40 × 0.36 ≈ 14.4 ms**, not the 5 ms rev 6 wrote. **The 40 ms target governs and the batch figure is derived from it**, because 40 ms is the number the data structures below were chosen to hit and the benchmark gate is written against it. CREATION_PLAN 5.2's feasibility claim survives the correction with room to spare — 15 s is seconds, not minutes — which is worth stating so nobody re-tightens the batch number to rescue an argument that does not need rescuing. If 4.3 measures materially above 40 ms, raise **both** numbers together and keep the 0.36 ratio between them.

**Cancellation means two different things here and only one of them exists.** A single `generatePreview` call is **not** cancellable (Sec.10 gives the reasons, and goal 4 is corrected to match); a 1000-run *batch* is cancellable **between runs**, since the loop is ours and can check a flag at each iteration boundary. That is what CREATION_PLAN 5.2's UX asks for and it costs nothing. Do not read this bullet as reinstating per-run cancellation.

**One cost this section does not otherwise account for.** Sec.10 rejects putting `refDb` in the message because it would structured-clone ~111 KB of JSON per keystroke burst — correct, and the data never changes — but `PreviewRequest` then carries the entire `ParseResult` on exactly the same schedule, and for a corpus map the AST is comparable in size or larger. It is already being cloned once by the parser worker, so this is a second clone of the same object. It is almost certainly still the right design (the AST *does* change every keystroke, so there is nothing to hoist), and it is called out because a section that quantifies worker boot and module init should not leave its largest per-request allocation unmentioned. **4.3 should measure it alongside the pipeline** and report both; if the clone dominates, the fix is a structural-sharing or transfer scheme, not a smaller budget.

**The 40 ms is only reachable with the right data structures, so they are part of the spec, not an optimization pass.** Two hot spots dominate, and rev 3 costed neither:

1. **Land growth.** A 200×200 map at `land_percent 100` is 40k tiles, each one a weighted draw from a frontier of hundreds of candidates. Re-normalizing weights per step is tens of millions of operations before objects are placed. Required: the frontier lives in **fixed integer weight buckets** (Sec.6.1 defines the bucket function), each bucket an append-only `Int32Array` of tile indices with a live count; a draw picks a bucket proportional to `count × weight` then an index within it, both O(1); membership is tracked in a `Uint8Array` so a tile is never enqueued twice, and stale entries are skipped lazily on pop rather than removed. No sorting, no re-weighting, no per-candidate object.
2. **Objects.** Naive cost is (per-command candidate scan over 40k tiles) × (8 player frames) × (N commands), plus a per-predicate intersection set for Sec.7 attribution, plus a BFS reachability mask per (land, habitat class), plus lazy distance transforms. Required: candidate sets are `Int32Array` index lists, not `Set`s; the *base* set per (reference frame, habitat class) is computed once per stage and cached, and each command **copies that cached base into a per-command scratch `Int32Array`** and write-compacts the scratch in place, one pass per predicate — which is also exactly what Sec.7's successive-intersection attribution needs, so attribution is free rather than an extra structure. **Copy, do not compact the cache itself**: the phrasing here through rev 5 said predicates "filter that list in place", which read literally destroys the cached base for every later command using the same frame, and the bug only shows up on the second `create_object` per frame — i.e. on almost every real map. One `.set()` per command buys both properties; reachability masks are cached per (land, habitat class) for the whole stage; distance transforms are computed lazily per (stage, terrainId) and invalidated on stage boundaries. A* uses a binary heap.

Other techniques: typed arrays only, no per-tile objects. Snapshots are the only large allocations.

**Benchmark and gate.** Vitest benchmark with a 10×-observed threshold, same flake philosophy as parser-design Sec.9. The 40 ms figure is the *design target* the structures above are chosen to hit; the benchmark threshold is what actually gates merges, and 4.3 should report the measured number rather than assert the target was met. If the measured cost lands materially above 40 ms after the structures above are in place, raise the number in this doc rather than leaving a spec nobody can satisfy under a do-not-deviate banner.

## 13. Test plan

**Determinism (bedrock):** same (parse, settings, seed) → deep-equal PreviewResult, asserted over 3 corpus maps × 3 seeds. Separate test: different seeds → different land origins (sanity that the seed is actually consumed).

**Instrumentation unit tests — one per FailureBucket:** a crafted minimal script per bucket asserting exactly that bucket fires with the right span/entity (e.g. `create_object GOLD { terrain_to_place_on SNOW }` on a snowless map → `terrainAbsent`; `min_distance_to_players 20 max_distance_to_players 10` → `minExceedsMax`; cost-0 moat → `connectionBlocked`; 10 lands on a Tiny map with huge min_placement_distance → `originFallbackCenter`). These are 5.2's foundation and gate merges.

**Rev-2 regression fixtures (pin the critique fixes):** (1) map-size labels — a script with an `if TINY_MAP / elseif LARGE_MAP / elseif MAPSIZE_LARGE` chain asserting Normal (200×200) selects the `LARGE_MAP` branch and Large (220×220) the `MAPSIZE_LARGE` branch (the offset table, Sec.4); (2) implicit terrain-separation — a two-island water map with `set_place_for_every_player` gold asserting every placed mine sits on its owner's island, and the same script with `ignore_terrain_restrictions` asserting the check lifts.

**Semantics units:** math evaluator against parser-design Sec.2.2's full example set (left-to-right, nested-paren drop, `%` truncation, `% 0`, `/0`, inf flooring idiom — same fixtures as the parser's, asserting *values* where the parser asserts *assembly*); instantiation (if/elseif selection, start_random cumulative ranges incl. >99 unreachable and <100 no-branch, first-const-wins, predefined shadowing no-op, behavior_version tile accounting, override_map_size clamp); scaling arithmetic — **two cases, and the second one is the one that matters.** (a) `create_elevation … number_of_tiles 400 set_scale_by_size` on Small asserts **829**, not the guide's 840 (Sec.4: exact `400 × 144²/10000 = 829.44`, **truncated**; the guide's 840 is its rounded ratio column applied by hand, and rev 3 asserted it against a formula that cannot produce it). (b) `create_object … number_of_objects 500 set_scaling_to_map_size` on Small asserts **1036**, exact value 1036.8. **Case (b) is not optional**, because case (a) cannot distinguish the rounding rule at all: 829.44's fraction is below .5, so floor and round-half-up agree on it, which is the very reason Sec.4 gives for the original measurement being unable to settle the question. Revisions 3 through 6 wrote "round half up" in this line — the rule Sec.4 withdrew in capitals — and a fixture asserting the right number while teaching the wrong rule is worse than no fixture. Both values are measured (2026-07-31); duplicate-attribute last-wins vs repeatable accumulation (the accumulation case reads the `repeatable` flag from `language.json`, so the fixture doubles as a regression test that the data is still flagged).

**Teams (Sec.3.1) — a pure function, so test it as one.** Canonicalisation is `(teams, playerCount) → { canonical, teamCount }` with no I/O and no randomness, which makes it the cheapest thing in the spec to get right and the easiest to get silently wrong. Cases that must be asserted, each pinning a specific way an implementer goes astray: (1) **renumbering** — selected `-,3,3,-,1,1,2,-` at 8 players → canonical `0,1,1,0,2,2,0,0`, i.e. selected 3 becomes canonical 1 because player 2 appears first, and the lone selected-2 drops to un-teamed; (2) **the ≥2 rule** — one player alone on team 1 → `0_TEAM_GAME`, `TEAM0_SIZE1`, `PLAYER1_TEAM0`, never `1_TEAM_GAME`; (3) **the length-8 trap** — a 4-player game whose `teams` array still holds assignments at indices 4–7 must produce identical output to one where those entries are 0, since those players are not in the game (this is the regression that catches a generator reading all 8); (4) **FFA defines a label** — all un-teamed → `0_TEAM_GAME` defined, which the retired solo-team premise never did; (5) **every derived name resolves** — assert each emitted label is present in `predefinedLabels` rather than merely well-formed, across all lobbies reachable at ≤8 players. That last one is the mutation-test-able check: it is the assertion that would have caught construct-and-trust, and per CLAUDE.md it is worth deliberately feeding it `TEAM1_SIZE1` once to watch it go red before trusting it green.

**Test (5) must also assert the other direction, per category — and note carefully what it can and cannot assert.** One-directional "everything emitted exists" passes cleanly today and is why nobody noticed the `playerInTeam` problem (Sec.3.1). The other direction is *not* set equality, and writing it that way would simply make the suite red: enumerate all lobbies at 2–8 players, collect the emitted set per category, and assert

- `teamCount`, `teamSize`, `playerCount`: **emitted set == data set**, exactly. `teamSize` is 29 of 29 and this is the check that turns Sec.3.1's reachability argument into a gate rather than a paragraph.
- `playerInTeam`: emitted set == data set **minus exactly the six names Sec.3.1 lists as unreachable** (`PLAYER1_TEAM2/3/4`, `PLAYER2_TEAM3/4`, `PLAYER3_TEAM4`). Written as an explicit expected-difference list, not as a tolerance. **The point of writing it this way is that it goes red if step 3's numbering rule changes** — which is exactly what happens if Sec.15 item 17 resolves the other way, and then the six-name list is deleted and the assertion becomes plain equality. A test that quietly passes under both rules would be worthless here.

Mutation-test it: delete one name from the expected-difference list and confirm red.

**Statistical (tolerance, fixed seeds, N=50):** `land_percent 40` single land → coverage within ±10 pp; `other_zone_avoidance_distance 10` two-zone map → min inter-zone gap ≥ 8 tiles in ≥95% of runs; placed objects always satisfy their min/max distance bands (hard invariant, not statistical); **land fragmentation tracks `clumping_factor`** — `cf 20`, `40` and `100` each give exactly 1 connected piece in every run (a hard invariant, and the cheapest possible regression on Sec.6.1's reservoir: a mis-set `w(cf)` fails it immediately), while `cf −20` gives >1 in the majority of runs and undershoots its tile budget.

**The elevation-bias test is REPLACED, and the one it replaces would have been un-passable.** Revisions through rev 6 asserted "elevation south-bias measurably present without `enable_balanced_elevation` and reduced with it". Both halves are stale: Sec.6.2 withdrew the **axis** (it is the `y − x` diagonal, not south — the whole point of the `mean x` control), and withdrew the **effect size** (balanced against unbalanced measured 12.86 → 12.27, a 5% reduction, on a seed bias of 1.31:1). N=50 at fixed seeds cannot resolve 5%, so as written the test either fails or gets tuned until it passes, which is the worse outcome. Assert instead, on the `y − x` diagonal:

- **Seed bias**: over ≥500 drawn seeds, the favoured:disfavoured split is 1.3 : 1 ± 0.15. This is the quantity the model is *about* (Sec.15 item 11's method note), so it is the one to gate.
